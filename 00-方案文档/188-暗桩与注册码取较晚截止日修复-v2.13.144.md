## 一、用户原话（2026-07-24）

> 「当注册码 校验解码 后的 日期早于 暗桩的日期 时，则以暗桩的日期 为限，反之，则以 注册码 解码 校验成功后的 日期为限」

**字面分解**：

| 条件 | 实际生效截止日 |
|------|---------------|
| 注册码 RegDate **早于** 暗桩 ValidTo | 取 **ValidTo**（暗桩） |
| 注册码 RegDate **晚于或等于** 暗桩 ValidTo | 取 **RegDate**（注册码） |

**两个场景都是「取较晚者」 = Max 语义**！

## 二、当前 BUG（v2.13.135 Min 取较早 — 与用户原话相反）

**当前代码**（`RuntimeWindowGuard.GetEffectiveDeadline()`）：

## 三、修复方案（v2.13.144）

### 3.1 新逻辑：取较晚者（Max）

```csharp
public static DateTime GetEffectiveDeadline()
{
    var tamperLimit = ValidTo;
    try
    {
        var reg = RegisterSdk.CheckReg();
        if (reg.RegInt == 1 && reg.RegDate.HasValue)
        {
            // v2.13.144 取较晚者（用户原话语义）：
            // - RegDate < ValidTo  → 截止 = ValidTo（暗桩较晚，取暗桩）
            // - RegDate >= ValidTo → 截止 = RegDate（注册码较晚，取注册码）
            return reg.RegDate.Value > tamperLimit ? reg.RegDate.Value : tamperLimit;
        }
    }
    catch { }
    return tamperLimit;
}
```

### 3.3 暗桩的兜底作用仍然保留

| 场景 | 行为 |
|------|------|
| 注册无效 / 未注册 | 截止 = ValidTo（暗桩），保留暗桩兜底 |
| RegDate 缺失（数据损坏）| 截止 = ValidTo（暗桩），保留暗桩兜底 |
| 当前时间 > ValidTo（暗桩已过）| `CheckExpiry()` 返回 overdueDays，触发 TamperDialog（不变）|
| 当前时间 < ValidFrom（暗桩未到）| `CheckExpiry()` 返回 -1，静默退出（不变）|

## 五、3 条永久教训

### 5.1 「取较早」≠「更严格」=「用户友好」

v2.13.135 的设计者把 Min 解释为"更严格"，但**严格的本质是限制未授权用户**，**不应限制付费用户**。暗桩的正确角色是「兜底」（未付费时用），而非「限制」（付费后仍用）。

### 5.2 安全机制 × 商业逻辑冲突时

当"取较早"看似更安全但实际损害付费用户权益时，应该**优先商业逻辑**——付费用户能用到所付金额对应的时间，是基本信任。暗桩防破解的兜底作用（未注册/数据损坏场景）仍保留 Max 不影响。

### 5.3 用户原话 vs 设计者原意冲突时

v2.13.135 设计者的注释"更严格"是**主观解释**，但**用户原话是客观需求**。当两者冲突时，永远按用户原话实现。**`if/else` 分支 + 注释 + 业务直觉必须字面对齐**。
