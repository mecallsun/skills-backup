## 1. 规范要求

> **筛选项**：住宿状态下拉列表数据统一关联引用"基础资料-住宿状态"列表定义的**主键 id**  
> **列表项**：列表"住宿状态"列关联引用**人员清单**中的"住宿状态"字段值/显示名称

### 1.1 数据链路

```
筛选下拉（fReside）
    │
    ├─ value: RESIDENCE_STATUS.id（FK 主键，1/2/3）
    │
    └─► EMPLOYEE_BILLS 筛选逻辑
            │
            ├─► getPersonnelResidenceId(b.employeeId)
            │       │
            │       ├─ 优先：PERSONNEL.residenceStatusId（FK，单一数据源）
            │       └─ 兜底：getEmployeeResidenceId()（基于 BOOKINGS 推导）
            │
            └─► 比对 RESIDENCE_STATUS.id

列表"住宿状态"列（residenceStatusBadge）
    │
    ├─► getPersonnelResidenceId(b.employeeId)
    │
    └─► RESIDENCE_STATUS.color / .name
```

**核心原则**：列表列与筛选下拉**同源**（both from PERSONNEL.residenceStatusId）。

## 2. 修复背景

### 2.1 v2.11.30 诊断发现的两个问题

| # | 问题 | 根因 | 影响 |
|---|------|------|------|
| 1 | employee-bills 列表缺少"住宿状态"列 | v2.11.21 重命名"住宿状态"列→"账单段类型"后未补回住宿状态列 | 列表无法识别员工住宿状态 |
| 2 | `PERSONNEL.residenceStatusId` 全部为 null | normalizeData IIFE 内同步逻辑被跳过（typeof 检查恒为 false）| 列表只能回退到 BOOKINGS 推导，与筛选下拉不同源 |

### 2.2 IIFE 时序问题详解

**v2.11.25 修复** 将 `RESIDENCE_STATUS` 和 `BOOKING_STATUS_DICT` 从 `const` 改为 `var` 并提前到 IIFE 之后。

**遗留问题**：`getLatestValidBooking` 和 `getResidenceStatusCode` 仍在 IIFE **之后**定义，但 IIFE 内的同步块依赖它们：

```javascript
// mock-data.js normalizeData IIFE（line 51652-51936）
if (typeof getResidenceStatusCode === 'function' && typeof RESIDENCE_STATUS !== 'undefined') {
    // IIFE 执行时 RESIDENCE_STATUS 尚未初始化（var 提升但未赋值）
    // getResidenceStatusCode 还未声明
    // typeof 全部为 'undefined' / 'undefined'
    // 整个同步块被跳过 → PERSONNEL.residenceStatusId 全部为 null
}
```

## 3. 修复方案

### 3.1 mock-data.js — 三处修复

**修复 1**：将 `getLatestValidBooking`、`getResidenceStatusCode`、`getResidenceStatusByCode` 全部提前到 IIFE 之后、`RESIDENCE_STATUS` 之后

```javascript
// v2.11.30 新增：在 RESIDENCE_STATUS 定义之后补充
function getLatestValidBooking(empId) { ... }
function getResidenceStatusCode(p) { ... }
function getResidenceStatusByCode(code) { ... }
```

**修复 2**：从 normalizeData IIFE 中移除"同步 PERSONNEL.residenceStatusId"块（该块依赖在 IIFE 之后才声明的函数）

**修复 3**：在所有 helper 函数定义完毕之后，添加独立同步块：

```javascript
// v2.11.30 独立同步块（在 IIFE 之外、依赖函数定义之后）
if (typeof getResidenceStatusCode === 'function' && typeof RESIDENCE_STATUS !== 'undefined') {
    let residenceSynced = 0;
    PERSONNEL.forEach(p => {
        const code = getResidenceStatusCode(p);
        const rs = RESIDENCE_STATUS.find(function (r) { return r.code === code; });
        if (rs) {
            const oldId = p.residenceStatusId;
            p.residenceStatusId = rs.id;
            p.residenceStatusCode = rs.code;
            p.residenceStatusName = rs.name;
            if (oldId !== rs.id) residenceSynced++;
        }
    });

    if (typeof console !== 'undefined' && console.log) {
        console.log('[v2.11.30 BUGFIX] PERSONNEL.residenceStatusId 与 ResidenceStatus 同步完成：');
        console.log('  住宿状态同步：' + residenceSynced + ' 条');
        console.log('  已住宿(LODGED)：' + PERSONNEL.filter(p => p.residenceStatusId === 1).length + ' 人');
        console.log('  未住宿(NOT_LODGED)：' + PERSONNEL.filter(p => p.residenceStatusId === 2).length + ' 人');
        console.log('  待入住(PENDING)：' + PERSONNEL.filter(p => p.residenceStatusId === 3).length + ' 人');
    }
}
```

**新增 helper 函数**：
```javascript
// 通过 employeeId 关联引用 PERSONNEL.residenceStatusId（基础资料-住宿状态 FK）
function getPersonnelResidenceId(empId) {
    if (typeof PERSONNEL === 'undefined') return null;
    for (var i = 0; i < PERSONNEL.length; i++) {
        if (PERSONNEL[i].id === empId) {
            if (PERSONNEL[i].residenceStatusId !== undefined && PERSONNEL[i].residenceStatusId !== null) {
                return PERSONNEL[i].residenceStatusId;
            }
            // 兜底：residenceStatusId 缺失时回退到 getEmployeeResidenceId（基于 BOOKINGS 推导）
            return getEmployeeResidenceId(empId);
        }
    }
    return null;
}

// 渲染住宿状态 Badge（关联引用 RESIDENCE_STATUS 字典）
function residenceStatusBadge(empId) {
    var resideId = getPersonnelResidenceId(empId);
    if (resideId === null) return '<span class="text-muted">-</span>';
    // ...遍历 RESIDENCE_STATUS 渲染 Badge...
}
```

## 6. 规范强化（v2.11.30）

### 6.1 字典关联引用规范（完善版）

| 规则 | 说明 |
|------|------|
| R-DICT-01 | 字典访问必须使用 `typeof X !== 'undefined'` 守卫 |
| R-DICT-02 | 字典渲染必须遍历字典数组，禁止硬编码映射 |
| R-DICT-03 | 字典字段使用 `.find()` 提取，禁止直接索引 |
| R-DICT-04 | 字典修改必须同步所有引用页面 |
| R-DICT-05 | 新增字典项必须同步更新所有引用页面的初始化逻辑 |
| R-DICT-06 | 所有下拉筛选 value 一律使用 FK 主键（id） |
| R-DICT-07 | 跨字典关联场景必须在文档中明确数据来源与联动规则 |
| R-DICT-08 | 业务枚举允许保留字符串，但基础资料字典必须 FK id |
| R-DICT-09 | 跨字典派生字段必须封装为 helper 函数 |
| **R-DICT-10**（v2.11.30 新增）| **同一字段的"筛选下拉 value"与"列表列数据源"必须同源（同 FK、同 helper）** |
| **R-DICT-11**（v2.11.30 新增）| **IIFE 时序问题排查：sync 块依赖的函数必须在 IIFE 执行前完成定义，或 sync 块必须移出 IIFE** |

### 6.2 mock-data.js 执行顺序约束

```
执行顺序（强约束）：
1. PERSONNEL, BOOKINGS, DORMS, ... (基础数据)
2. normalizeData IIFE（可包含基础字段规范化，但不得依赖运行时函数）
3. 基础资料字典：RESIDENCE_STATUS, BOOKING_STATUS_DICT, ...（var 或 const）
4. 跨字典派生函数：getResidenceStatusCode, getResidenceStatusByCode, ...
5. 跨数据源同步块：PERSONNEL.residenceStatusId 同步（依赖步骤 3、4）
6. 后续业务函数 / 页面脚本
```

> **禁止**：在 IIFE 内部使用跨字典派生函数（即使加 typeof 守卫，也会因为时序问题被静默跳过）。
