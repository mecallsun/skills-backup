## v2.13.48 增量说明（2026-07-21）

**v2.13.47 增量：EmployeeCode FK 同步策略**

住宿登记的员工信息以**人员清单的 `SysEmployee.Id`（员工记录 ID）**为 FK 存入 `DormBooking.EmployeeId` 字段，列表显示员工信息（工号、姓名、部门、考勤班次等）时必须通过 `EmployeeId` JOIN `SysEmployee` 实时取最新档案数据，**禁止直接读 `DormBooking.EmployeeCode` / `EmployeeName` 等冗余字段**。

详见 `100-Booking工号同步BUG修复-v2.13.47.md` 完整 BUG 修复报告。

### 核心数据关系（v2.13.47 起强制）

```
SysEmployee (人员清单 — 唯一真源)
   ├─ Id (PK, int)                    ← 员工记录 ID
   ├─ EmployeeCode (NVARCHAR 64)      ← 工号（人员清单档案）
   ├─ RealName (NVARCHAR 128)         ← 姓名（人员清单档案）
   ├─ Phone / Department / AttendanceTypeId / ResidenceStatusId / ...
   │
   └─ 1:N ──→ DormBooking (办理登记 — 冗余字段仅用于历史追溯)
                ├─ EmployeeId (FK → SysEmployee.Id, NOT NULL)
                ├─ EmployeeCode (冗余快照，运行时被 SysEmployee.EmployeeCode 覆盖显示)
                ├─ EmployeeName (冗余快照，运行时被 SysEmployee.RealName 覆盖显示)
                ├─ Phone / Department / AttendanceTypeId (冗余快照，同理覆盖)
                └─ DormCode (FK → Dorm.DormCode)
```

**FK 关联优先级**：
1. **`EmployeeId` 优先**（v2.13.x 起 DormBooking.EmployeeId 必填，JOIN 关系稳定）
2. **`EmployeeCode` 次之**（兼容历史数据中 EmployeeId=0 的孤儿记录，Repair API 用作反查）

**查询时显示字段同步策略**（v2.13.33 + v2.13.47 双管齐下）：

| 显示字段 | 数据源（运行时实时覆盖） | 写入 DB 时机 | v2.13.x 关键版本 |
|---------|----------------------|------------|:-----------:|
| `EmployeeCode` 工号 | `SysEmployee.EmployeeCode` JOIN 实时取 | Repair API 一次性写回 | **v2.13.47 新增** |
| `EmployeeName` 姓名 | `SysEmployee.RealName` JOIN 实时取 | Repair API 一次性写回 | v2.13.33 |
| `Department` 部门 | `SysEmployee.Department` JOIN 实时取 | Repair API 一次性写回 | v2.13.33 |
| `AttendanceTypeId` 考勤班次 | `SysEmployee.AttendanceTypeId` JOIN 实时取 | Repair API 一次性写回 | v2.13.24 |
| `Phone` 手机号 | `SysEmployee.Phone` JOIN 实时取 | Repair API 一次性写回 | v2.13.24 |

**禁止用法**：在 `BookingService.GetListAsync` 或任何展示 `DormBooking` 列表的查询中**直接 select `b.EmployeeCode` 或 `b.EmployeeName`** 作为展示字段，必须通过 JOIN `SysEmployee` 取最新档案值。

## v2.13.33 增量说明（保留作为历史版本）

**办理登记数据关系补充**：
- `DormBooking.EmployeeName` 是 v2.11.x 引入的反范式冗余字段（写入时快照）。
- **v2.13.33 起 EmployeeName 同步双管齐下**：
  1. **运行时实时覆盖**：`BookingService.GetListAsync` 用 `SysEmployee.RealName` 覆盖显示的 `EmployeeName`（仅 RAM，不写 DB）。
  2. **一次性写回**：`POST /api/v1/bookings/repair-employee-names` 把所有不一致记录写回 DB + UpdatedAt。
- `/Booking` 页面 PageHeader 新增「修复姓名关联」橙色按钮触发一次性写回。

## 三、跨页面数据流转

### 3.1 入住办理流程

```
人员清单 (新增员工)
  │
  ├─ 填写员工信息（工号、姓名、部门、员工类型、班组、考勤班次、性别等）
  │
  ├─ 设置 DormCode = 空 → 未住宿
  │
  ▼
办理登记 → 入住办理 (CheckIn)
  │
  ├─ 选择员工（v2.13.113 selectEmp 立即显示 emp-info-card：工号/姓名/性别/手机/部门/类型/班次/班组 8 字段 FK 显示）
  │
  ├─ 校验员工（v2.12.34）：当前在宿 / 入住日期 vs 入职日期
  │
  ├─ 自动加载可分配房号下拉（v2.13.84+v2.13.112 三层过滤 + 4 级排序）：
  │   ├─ L1 余量过滤：available > 0
  │   ├─ L2 性别过滤：男不入女、女不入男、空房放行（详见 07-办理登记需求 §7.1 R2 矩阵）
  │   ├─ L3 完全空房间放行（任何性别）
  │   └─ 排序：同员工班组 (P1) > 空房 (P2) > 同班次 (P3) > 字典序 (P4)
  │   └─ 每项显示：房号 + 楼栋 + 地址 + 班组 A/B/C + 床位 N/M
  │
  ├─ 校验：宿舍容量未满、性别一致、班组优先
  │
  ├─ 创建 DormBooking 记录 (Type=1, Status=2)
  │
  ├─ 更新 SysEmployee.DormCode = 宿舍代码 + BedNo = 床位号
  │
  ├─ 更新 SysEmployee.ResidenceStatusId = 1 (已住宿)
  │
  ▼
宿舍详情 → 入住人数 +1
```

### 3.2 退房办理流程

```
办理登记 → 退房办理 (CheckOut)
  │
  ├─ 选择员工 → 确认退房
  │
  ├─ 创建 DormBooking 记录 (Type=2, Status=3)
  │
  ├─ 更新 SysEmployee.DormCode = NULL
  │
  ├─ 更新 SysEmployee.ResidenceStatusId = 2 (未住宿)
  │
  ▼
宿舍详情 → 入住人数 -1, 入住率下降
```

### 3.3 抄表与费用计算流程

```
智能抄表 → 手动录入 / PDA 上传
  │
  ├─ 选择宿舍 → 选择月份
  │
  ├─ 录入冷水表、热水表、电表读数
  │
  ├─ 系统自动计算用量（本期读数 - 上期读数）
  │
  ├─ 校验：同宿舍同月唯一
  │
  ▼
费用标准 (HotWaterPrice / ColdWaterPrice / ElectricityPrice)
  │
  ├─ 计算宿舍总费用 = Σ(用量 × 单价)
  │
  ▼
宿舍账单 (DormBilling)
  │
  ├─ 按入住人数分摊
  │
  ▼
员工账单 (EmployeeBilling)
  │
  ├─ 显示每人应付金额
  │
  ▼
首页 KPI → 人均费用、本月费用合计
```

## 四、首页 KPI 数据源

| KPI | 数据源 | 计算公式 |
|-----|--------|---------|
| 入住人数 | `SysEmployee` | COUNT(DormCode IS NOT NULL) |
| 宿舍入住率 | `Dorm.Capacity` | 入住人数 / ΣCapacity × 100% |
| 预约人员 | `DormBooking` | COUNT(Status=1 且 BookingDate < Today) |
| 异常人员 | `SysEmployee` | (在职状态≠1 且 DormCode 非空) + (在职且未到入职日期) + (预约超期未办) |
| 本月抄表覆盖 | `MeterRecord` | COUNT(本月有记录) / COUNT(Dorm) |
| 人均费用 | `EmployeeBilling` | SUM(TotalShareAmount) / COUNT(账单) |
| 本月费用合计 | `DormBilling` | SUM(宿舍总费用) |

## v2.13.111 备注：宿舍档案列表「班组」列派生数据关系

**派生起点**：`DormBooking (Status=2 在宿)`（无 schema 迁移，纯运行时派生）

**派生链路**：

```
Dorm.DormCode ─(FK)─→ DormBooking.DormCode WHERE Status = 2 ─(FK EmployeeId)─→ SysEmployee.Id
  ↓
SysEmployee.TeamId ─(FK)─→ Team.Id
  ↓
Team.Name (显示) + Team.SortOrder (排序)
```

**业务规则**：

1. 仅统计 `Status = 2`（已入住）的人员，预约（Status=1）/ 已退房（Status=3）/ 已取消（Status=4）不计入
2. 按 `Team.SortOrder` 升序 + `Team.Id` 二级排序
3. 同 TeamId 去重仅保留一个
4. 无人入住时 `TeamNames` 为空，UI 渲染 `<td>` 完全空白（无任何字符）
5. 员工 `TeamId` 孤儿（Team 表不存在）由 INNER JOIN 自动过滤

**同步模式**：

| 模块 | 列名 | 派生模式 | 版本 |
|------|------|---------|------|
| 宿舍详情 | 当前入住人员「班组」 | 1 个房间的 DormBooking JOIN | v2.13.91 |
| 住宿登记 | 列表「班组」 | 1 条 Booking 的 Employee JOIN | v2.13.97 |
| 宿舍档案 | 列表「班组」 | 当前页所有房间批量 DormBooking JOIN | **v2.13.111** |

**核心原则**：人员档案为唯一真源，`SysEmployee.TeamId` FK → `Team.Name`，所有派生通过 JOIN 实时计算，不缓存到 Dorm 表。

**详细交付报告**：`00-方案文档/163-宿舍档案列表班组列-v2.13.111.md`
