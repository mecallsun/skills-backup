## 1. 业务背景

### 1.1 名称变更

| 旧名 | 新名 |
|------|------|
| 住宿记录 | **办理登记** |

### 1.2 功能升级

原「住宿记录」只展示员工的入住/退宿状态，本次升级为完整 CRUD：
- 可对单个记录进行新增、修改、删除
- 按员工姓名/工号/手机号模糊查询
- 选择员工后自动带出手机号 + 部门
- 操作类型（入住 / 退房）显式区分
- 房间列表自动过滤「有余量」+「日期不冲突」的房间
- 严格的一进一出日期重叠校验

## 2. 业务规则

### 2.1 一进一出日期重叠校验（核心）

| 规则 | 说明 |
|------|------|
| R-BOOK-01 | **同一员工**的办理登记按时间排序必须交替：入住 → 退房 → 入住 → 退房 ... |
| R-BOOK-02 | 同一员工的**同日不能既有入住又有退房**（重叠校验） |
| R-BOOK-03 | 新入住日期必须 **≥ 上一次退房日期 + 1 天**（一进一出顺序） |
| R-BOOK-04 | 新退房日期必须 **≥ 上一次入住日期** 且 **≤ 下一次入住日期 - 1 天** |
| R-BOOK-05 | 入住日期不能早于员工入职日期 |
| R-BOOK-06 | 退房日期不能晚于今天 |

### 2.2 房间余量校验

| 规则 | 说明 |
|------|------|
| R-BOOK-07 | 入住时房间余量 = 房间容量 - 当前在宿人数 - **预约入住**人数 |
| R-BOOK-08 | 退房时记录必须存在且状态为「在宿」 |
| R-BOOK-09 | 退房后该记录状态变为「已退房」，员工变为未分配住宿 |

### 2.3 状态机

```
[预约入住] --实际入住日到达--> [在宿]
[在宿]    --办理退房---------> [已退房]（创建 Type=2 退房新记录）
[在宿]    --今日撤销---------> [已取消]（仅 BookingDate=今天，Type=1 入住 && Status=2 在宿）
[预约入住] --取消-------------> [已取消]
[预约退房] --实际退房--------> [已退房]
[预约退房] --取消-------------> [已取消]
```

## 3. 数据模型（替代 DormResidency）

> ### ⚠️ v2.13.47 强制数据关系（2026-07-21 BUG 修复后定稿）
>
> **住宿登记的员工信息以 `SysEmployee.Id`（人员清单的员工记录 ID）作为 FK 存入 `DormBooking.EmployeeId` 字段**。
> 列表展示员工信息（工号、姓名、部门、考勤班次等）必须通过 `EmployeeId` JOIN `SysEmployee` 实时取最新档案数据，**禁止直接读 `DormBooking.EmployeeCode` / `EmployeeName` 等冗余字段**作为展示字段。
>
> **冗余字段定位**：`DormBooking.EmployeeCode` / `EmployeeName` / `Phone` / `Department` 仅作为**写入时快照 + 历史追溯**用途，运行时展示数据必须以人员清单（SysEmployee）为唯一真源。
>
> **同步策略**：v2.13.33 起 EmployeeName 同步双管齐下；v2.13.47 起扩展到 EmployeeCode（详见 100-Booking工号同步BUG修复-v2.13.47.md）。
>
> ```sql
> -- 正确：通过 FK JOIN 取实时档案（推荐）
> SELECT b.Id, b.EmployeeId,
>        e.EmployeeCode,  -- 来自 SysEmployee（人员清单真源）
>        e.RealName,      -- 来自 SysEmployee（人员清单真源）
>        e.Department,    -- 来自 SysEmployee（人员清单真源）
>        e.AttendanceTypeId, -- 来自 SysEmployee（人员清单真源）
>        b.DormCode, b.Type, b.BookingDate, b.Status
> FROM DormBooking b
> INNER JOIN SysEmployee e ON b.EmployeeId = e.Id
>
> -- 错误：直接读 DormBooking 冗余字段（v2.13.47 起禁止）
> SELECT b.Id, b.EmployeeId, b.EmployeeCode, b.EmployeeName, ...
> FROM DormBooking b
> ```

### 3.1 DormBooking 办理登记表

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| Id | INT | PK | 主键自增 |
| **EmployeeId** | INT | 是 | **FK→SysEmployee.Id（人员清单的员工记录 ID，唯一真源关联键）** |
| EmployeeCode | NVARCHAR(20) | 是 | 冗余（写入时快照，运行时被 SysEmployee.EmployeeCode 覆盖显示 — v2.13.47） |
| EmployeeName | NVARCHAR(50) | 是 | 冗余（写入时快照，运行时被 SysEmployee.RealName 覆盖显示 — v2.13.33） |
| Phone | NVARCHAR(20) | 否 | 冗余（运行时被 SysEmployee.Phone 覆盖显示） |
| Department | NVARCHAR(50) | 否 | 冗余（运行时被 SysEmployee.Department 覆盖显示） |
| DormCode | NVARCHAR(20) | 是 | FK→Dorm.DormCode |
| **Type** | TINYINT | 是 | **1=入住 2=退房** |
| **BookingDate** | DATE | 是 | **预计/实际入退日期**（前台录入） |
| **Status** | TINYINT | 是 | **1=预约 2=在宿 3=已退房 4=已取消** |
| Reason | NVARCHAR(200) | 否 | 原因（入职、调岗、离职、换房等） |
| Remark | NVARCHAR(500) | 否 | 备注 |
| **RegistrationDate** | DATETIME | 是 | **实际登记日期（默认 now()）** |
| **Registrar** | NVARCHAR(50) | 是 | **登记人（当前登录用户名）** |
| CreatedAt | DATETIME | 是 | — |
| UpdatedAt | DATETIME | 否 | — |

**索引**：
- `IX_DormBooking_Employee` (EmployeeId, BookingDate DESC)
- `IX_DormBooking_Dorm` (DormCode, BookingDate DESC)
- `UX_DormBooking_EmployeeTypeDate` UNIQUE (EmployeeId, Type, BookingDate) — 防止同一员工同一天重复登记
- `IX_DormBooking_Status` (Status, BookingDate)

**FK 关联查询实现**（v2.13.47 起标准模板）：
```csharp
// 正确：通过 EmployeeId FK JOIN SysEmployee 取实时档案
var query =
    from b in _db.DormBookings
    join emp in _db.Employees on b.EmployeeId equals emp.Id into empGroup
    from emp in empGroup.DefaultIfEmpty()
    select new
    {
        Booking = b,
        // 运行时实时取（人员清单为唯一真源）
        EmployeeCode = emp != null && !string.IsNullOrEmpty(emp.EmployeeCode) ? emp.EmployeeCode : b.EmployeeCode,
        RealName = emp != null && !string.IsNullOrEmpty(emp.RealName) ? emp.RealName : b.EmployeeName
        // ... 其他字段同理
    };
```

### 4.1 快速确认入住接口契约（v2.11.8 新增）

**请求**：`POST /api/v1/bookings/{id}/confirm-checkin`

**请求体**：空（仅依赖路径参数 id）

**校验**（后端强制）：
| # | 校验项 | 触发条件 | 错误码 |
|---|--------|---------|--------|
| V-CONFIRM-01 | 记录存在 | id 无效 | `404 NOT_FOUND` |
| V-CONFIRM-02 | Type=1 入住 | Type≠1 | `400 INVALID_TYPE`：`仅 Type=1 入住类型可快速确认` |
| V-CONFIRM-03 | Status=1 预约 | Status≠1 | `400 INVALID_STATUS`：`仅 Status=1 预约状态可快速确认` |
| V-CONFIRM-04 | **房间床位余量** | 入住时 `Dorm.CurrentResidentCount < Dorm.Capacity` | `400 NO_CAPACITY`：**`床位已满，请更换其他房间`**（v2.11.8.b 优化提示文案） |

**响应**（成功）：

```json
{
  "success": true,
  "data": {
    "id": 12345,
    "status": 2,
    "statusName": "在宿",
    "registrar": "admin",
    "registrationDate": "2026-07-12T15:30:00",
    "updatedAt": "2026-07-12T15:30:00"
  }
}
```

**服务端逻辑**：
```
1. 加载 DormBooking[id]，若不存在 → 404
2. 若 Type ≠ 1 → 400 INVALID_TYPE
3. 若 Status ≠ 1 → 400 INVALID_STATUS
4. **校验房间床位余量**：`Dorm.CurrentResidentCount < Dorm.Capacity`
   - 满足 → 进入步骤 5（事务写入）
   - **不满足 → 返回 400 NO_CAPACITY，提示文案："床位已满，请更换其他房间"**（v2.11.8.b 优化）
5. 事务内：
   ├─ DormBooking.Status = 2
   ├─ DormBooking.Registrar = 当前登录用户名
   ├─ DormBooking.RegistrationDate = now()
   ├─ DormBooking.UpdatedAt = now()
   └─ SysEmployee.DormCode = 该记录 DormCode（联动同步）
6. 返回 ApiResponse { success: true, data: 更新后的记录 }
```

### 4.2 撤销退房接口契约（v2.11.10 新增）

**请求**：`POST /api/v1/bookings/{id}/undo-checkout`

**请求体**：空（仅依赖路径参数 id）

**校验**（后端强制）：
| # | 校验项 | 触发条件 | 错误码 |
|---|--------|---------|--------|
| V-UNDO-01 | 记录存在 | id 无效 | `404 NOT_FOUND` |
| V-UNDO-02 | Status=3 已退房 | Status≠3 | `400 INVALID_STATUS`：`仅 Status=3 已退房可撤销` |
| V-UNDO-03 | 入退日期 = 服务端今天 | BookingDate ≠ 今天 | `400 NOT_TODAY`：`仅入退日期为今天的记录可撤销` |
| V-UNDO-04 | **房间床位余量** | 入住时 `Dorm.CurrentResidentCount < Dorm.Capacity` | `400 NO_CAPACITY`：**`床位已满，撤销退房失败！`** |

**响应**（成功）：

```json
{
  "success": true,
  "data": {
    "id": 12345,
    "status": 2,
    "statusName": "在宿",
    "registrar": "admin",
    "registrationDate": "2026-07-12T15:30:00",
    "updatedAt": "2026-07-12T15:30:00"
  }
}
```

**服务端逻辑**：
```
1. 加载 DormBooking[id]，若不存在 → 404
2. 若 Status ≠ 3 → 400 INVALID_STATUS
3. 若 BookingDate ≠ today → 400 NOT_TODAY
4. **校验房间床位余量**：`Dorm.CurrentResidentCount < Dorm.Capacity`
   - 满足 → 进入步骤 5（事务写入）
   - **不满足 → 返回 400 NO_CAPACITY，提示文案："床位已满，撤销退房失败！"**（不修改任何字段）
5. 事务内：
   ├─ DormBooking.Status = 2（在宿）
   ├─ DormBooking.Registrar = 当前登录用户名
   ├─ DormBooking.RegistrationDate = now()
   ├─ DormBooking.UpdatedAt = now()
   └─ SysEmployee.DormCode = 该记录 DormCode（联动恢复）
6. 返回 ApiResponse { success: true, data: 更新后的记录 }
```

### 4.3 撤销预约接口契约（v2.11.11 新增）

**请求**：`POST /api/v1/bookings/{id}/cancel-reservation`

**请求体**：空（仅依赖路径参数 id）

**校验**（后端强制）：
| # | 校验项 | 触发条件 | 错误码 |
|---|--------|---------|--------|
| V-CANCEL-01 | 记录存在 | id 无效 | `404 NOT_FOUND` |
| V-CANCEL-02 | Status=1 预约 | Status≠1 | `400 INVALID_STATUS`：`仅 Status=1 预约可撤销` |

**响应**（成功）：

```json
{
  "success": true,
  "data": {
    "id": 12345,
    "status": 4,
    "statusName": "已取消",
    "registrar": "admin",
    "registrationDate": "2026-07-12T15:30:00",
    "updatedAt": "2026-07-12T15:30:00"
  }
}
```

**服务端逻辑**：
```
1. 加载 DormBooking[id]，若不存在 → 404
2. 若 Status ≠ 1 → 400 INVALID_STATUS
3. 事务内：
   ├─ DormBooking.Status = 4（已取消）
   ├─ DormBooking.Registrar = 当前登录用户名
   ├─ DormBooking.RegistrationDate = now()
   └─ DormBooking.UpdatedAt = now()
4. 返回 ApiResponse { success: true, data: 更新后的记录 }
```

> **与 v2.11.10 撤销退房的区别**：
> - **撤销退房**（v2.11.10）针对已退房（Status=3）记录的"误操作回退"，需校验房间余量；
> - **撤销预约**（v2.11.11）针对预约（Status=1）记录的"主动取消"，无需校验房间余量（从未入住）。

### 4.4 确认退房接口契约（v2.11.12 新增）

**请求**：`POST /api/v1/bookings/{id}/confirm-checkout`

**请求体**：空（仅依赖路径参数 id）

**校验**（后端强制）：
| # | 校验项 | 触发条件 | 错误码 |
|---|--------|---------|--------|
| V-CONFIRM-CO-01 | 记录存在 | id 无效 | `404 NOT_FOUND` |
| V-CONFIRM-CO-02 | Type=2 退房 | Type≠2 | `400 INVALID_TYPE`：`仅 Type=2 退房类型可确认` |
| V-CONFIRM-CO-03 | Status=1 预约 | Status≠1 | `400 INVALID_STATUS`：`仅 Status=1 预约状态可确认` |

**响应**（成功）：

```json
{
  "success": true,
  "data": {
    "id": 12345,
    "status": 3,
    "statusName": "已退房",
    "registrar": "admin",
    "registrationDate": "2026-07-12T15:30:00",
    "updatedAt": "2026-07-12T15:30:00"
  }
}
```

**服务端逻辑**：
```
1. 加载 DormBooking[id]，若不存在 → 404
2. 若 Type ≠ 2 → 400 INVALID_TYPE
3. 若 Status ≠ 1 → 400 INVALID_STATUS
4. 事务内：
   ├─ DormBooking.Status = 3（已退房）
   ├─ DormBooking.Registrar = 当前登录用户名
   ├─ DormBooking.RegistrationDate = now()
   ├─ DormBooking.UpdatedAt = now()
   └─ SysEmployee.DormCode = NULL（联动：员工变为未分配住宿）
5. 返回 ApiResponse { success: true, data: 更新后的记录 }
```

> **与现有 `/api/v1/bookings/{id}/check-out` 的区别**：
> - **check-out**（既有）：针对当前在宿（Status=2）的员工，需要选员工+在宿记录+输入退房日期走 4 步表单；
> - **confirm-checkout**（v2.11.12）：针对预约退房（Type=2 && Status=1）的记录，一键确认即变更为已退房。

### 4.5 撤销在宿接口契约（v2.11.17 新增）

> **业务场景**：员工当天办理入住后，发现信息有误或需要取消（如入退日期为当天），HR 可一键"撤销"该入住记录，将其状态改为"已取消"，**不创建新记录**。

**请求**：`POST /api/v1/bookings/{id}/cancel-today`

**请求体**：空（仅依赖路径参数 id）

**校验**（后端强制）：
| # | 校验项 | 触发条件 | 错误码 |
|---|--------|---------|--------|
| V-CANCEL-TODAY-01 | 记录存在 | id 无效 | `404 NOT_FOUND` |
| V-CANCEL-TODAY-02 | Type=1 入住 | Type≠1 | `400 INVALID_TYPE`：`仅 Type=1 入住类型可撤销` |
| V-CANCEL-TODAY-03 | Status=2 在宿 | Status≠2 | `400 INVALID_STATUS`：`仅 Status=2 在宿可撤销` |
| V-CANCEL-TODAY-04 | 入退日期 = 服务端今天 | BookingDate ≠ 今天 | `400 NOT_TODAY`：`仅入退日期为今天的记录可撤销` |

**响应**（成功）：

```json
{
  "success": true,
  "data": {
    "id": 12345,
    "status": 4,
    "statusName": "已取消",
    "registrar": "admin",
    "registrationDate": "2026-07-13T10:30:00",
    "updatedAt": "2026-07-13T10:30:00"
  }
}
```

**服务端逻辑**：
```
1. 加载 DormBooking[id]，若不存在 → 404
2. 若 Type ≠ 1 → 400 INVALID_TYPE
3. 若 Status ≠ 2 → 400 INVALID_STATUS
4. 若 BookingDate ≠ today → 400 NOT_TODAY
5. 事务内：
   ├─ DormBooking.Status = 4（已取消）
   ├─ DormBooking.Registrar = 当前登录用户名
   ├─ DormBooking.RegistrationDate = now()
   └─ DormBooking.UpdatedAt = now()
   （不联动 SysEmployee.DormCode，因为原记录仍在宿，只是取消本次登记）
6. 返回 ApiResponse { success: true, data: 更新后的记录 }
```

> **与 v2.11.11 撤销预约的区别**：
> - **撤销预约**（v2.11.11）：Status=1 预约 → 4 已取消（从未入住）；
> - **撤销在宿**（v2.11.17）：Status=2 在宿 → 4 已取消（已入住，但当天撤销），**不创建新记录**。

### 4.6 创建退房记录接口契约（v2.11.17 新增）

> **业务场景**：员工当前在宿（Type=1 入住 && Status=2 在宿），点击"退房"按钮后，**弹出一个确认对话框**，展示当前日期和类型为"退房"的信息，用户确认后：
> 1. 创建一条新的 Type=2 退房类型的 DormBooking 记录（BookingDate=今天）；
> 2. 将原入住记录的 Status 变更为 3 已退房；
> 3. 联动：`SysEmployee.DormCode = NULL`（员工变为未分配住宿）。

| V-CREATE-CO-02 | Type=1 入住 | Type≠1 | `400 INVALID_TYPE`：`仅 Type=1 入住类型可创建退房记录` |
| V-CREATE-CO-03 | Status=2 在宿 | Status≠2 | `400 INVALID_STATUS`：`仅 Status=2 在宿可创建退房记录` |

   ├─ ① 将原记录 DormBooking.Status = 3（已退房）
   ├─ ② 创建新记录：
   │    ├─ Type = 2（退房）

> - **check-out**（既有）：走 4 步表单，需选员工+选在宿记录+输入退房日期；
> - **confirm-checkout-create**（v2.11.17）：列表页"退房"按钮直接调用，弹出确认对话框后**自动创建一条 Type=2 退房的新记录**，无需手动选日期。

> - **confirm-checkout**（v2.11.12）：针对 Type=2 退房 && Status=1 预约的记录，一键确认即变更为已退房（**不创建新记录**）；

> - **原型实现**：使用 `registerList.reset()` 重新拉取数据 + 重新渲染；或 `render()` 函数触发列表重绘
> - **刷新范围**：至少刷新当前记录所在行；推荐刷新整个列表（保证筛选条件、分页、合计数等同步）

#### 规则 R9：**强锁定** 校验通过才解锁 dormSelect（v2.13.124 新增）

**用户原话**：「当选择了员工后，显示员工的档案信息，并**同时进行校验该员工是否符合入住**，提示校验信息；**当能校验通过，则解锁选择房号列表**」。

- **R9-A 触发时机**：`selectEmp` 函数内立即触发（在 R1 档案渲染之后、refreshDorms 之前）
- **R9-B validateEmp 返回值**：必须返回 `boolean`（`true`=通过 / `false`=失败），不再仅设置 UI 提示
- **R9-C 校验失败场景**：
  - 员工当前已在宿（`active.length > 0`，opType=1 入住模式）→ ❌ 锁定
  - API 网络错误 / 返回 5xx → ❌ 锁定（防御性）
- **R9-D 校验通过场景**：
  - 员工无历史记录（首次入住）→ ✅ 解锁
  - 员工上次已退房（Status=3 历史）→ ✅ 解锁
- **R9-E dormSelect 状态**：校验通过 → `disabled = false` + 调用 `refreshDorms()`；校验失败 → `disabled = true` + innerHTML 替换为「⚠️ 员工状态校验失败，请查看下方提示」
- **R9-F 业务哲学**：与 R2（过滤无效选项）不同，R9 是「阻止非法提交」业务硬约束（v2.13.82 三层防御规范的延伸）

**实现要点**：

```javascript
async function selectEmp(emp) {
    selectedEmp = emp;
    // ... 8 字段渲染 ...
    
    // R9 核心：先校验，再决定 dormSelect 状态
    const valid = await validateEmp();
    const dormSelect = document.getElementById('dormSelect');
    if (valid) {
        dormSelect.disabled = false;
        refreshDorms();
    } else {
        dormSelect.disabled = true;
        dormSelect.innerHTML = '<option value="">⚠️ 员工状态校验失败，请查看下方提示</option>';
    }
}

async function validateEmp() {
    if (!selectedEmp) return false;
    // ... 校验逻辑 ...
    if (opType === '1' && active.length > 0) {
        // 红色 alert-danger
        return false;  // 锁定
    }
    return true;  // 解锁
}
```

## 14. BUGFIX 记录：列表筛选房号条件失效（v2.11.14 修复）

### 14.1 问题描述

**用户反馈**：在办理登记列表的"房号"筛选输入框输入关键字（如"D"），列表返回空结果；但 mock 数据中存在大量房号以"D"开头的记录（如 `D-001`、`D-088`、`D-126` 等），预期应该返回这些记录。

**复现步骤**：
1. 打开 `04-HTML原型/booking/index.html` 办理登记列表
2. 在"房号"输入框输入"D"（或任意房号前缀字符）
3. 观察列表：返回 0 条结果（BUG）

**预期结果**：返回所有房号包含"D"的记录（约 750+ 条）。

### 14.2 根因分析

#### JavaScript 运算符优先级问题

原型 `getFiltered()` 函数原代码：

```javascript
if (dc && !(b.dormCode || "").toLowerCase().indexOf(dc) > -1) return false;
```

**问题分析**：JS 运算符优先级 `!` 高于 `>`，导致表达式解析为：

```javascript
if (dc && (!((b.dormCode || "").toLowerCase().indexOf(dc)) > -1)) return false;
```

逐步演算（以 `b.dormCode = "D-085"`、`dc = "d"` 为例）：

| 步骤 | 表达式 | 结果 |
|------|--------|------|
| 1 | `(b.dormCode || "").toLowerCase()` | `"d-085"` |
| 2 | `.indexOf("d")` | **`0`**（匹配位置 0） |
| 3 | `!0` | **`true`**（逻辑非） |
| 4 | `true > -1` | **`true`**（`true` 强转为 `1`，`1 > -1`） |
| 5 | `dc && true` | **`true`**（条件恒真） |
| 6 | `return false` | **执行**（错误地排除所有记录） |

**关键陷阱**：`indexOf()` 返回 `0` 时（命中位置在字符串开头），`!0 = true`，再加上 `true > -1` 也为 `true`，导致**条件恒真**，所有记录都被排除。

> 同文件中的 `keyword`（员工姓名/工号/手机号）与 `department` 筛选也存在相同 BUG 模式（但因 keyword 字段是用临时变量 `h` 串联 OR 表达式，部分场景下还能"侥幸"工作；`dc`（房号）则**完全失效**）。

### 14.3 修复方案

#### 方案 A：增加显式括号（最小修改）

```javascript
if (dc && ((b.dormCode || "").toLowerCase().indexOf(dc) > -1) === false) return false;
// 或等价写法
if (dc && ((b.dormCode || "").toLowerCase().indexOf(dc)) === -1) return false;
```

#### 方案 B：改用 === -1 判断（推荐，更易读）

```javascript
if (dc && (b.dormCode || "").toLowerCase().indexOf(dc) === -1) return false;
```

**最终采用方案 B**：语义最清晰（"未找到" = `indexOf === -1`），消除运算符优先级歧义。
