### 3.2 问题诊断（执行过程中发现）

1. **登录 500 错误的 7 层根因**（已全部定位）：
   - BCrypt 哈希 vs SHA256 哈希（数据库存的是旧 SHA256 哈希，C# 代码用 BCrypt 验证）
   - 账号锁定（admin 因 5 次失败被自动锁定，IsLocked=True）
   - Microsoft.Data.SqlClient 版本不匹配（5.2.0 vs 5.1.1）
   - DPAPI 加密实现正确（已验证）
   - 多表 schema 不匹配（`UserId` vs `Id`、`Mobile` vs `Phone`、`LastLoginAt` vs `LastLoginTime` 等 13+ 处字段差异）
   - `IHostedService.StartAsync` 阻塞 Kestrel 绑定端口（应改用 `BackgroundService`）
   - 托盘进程硬编码端口（5001/5000）与实际配置文件（5001/5100）不一致

2. **架构层面的可执行性验证**：
   - 托盘 → DB 预检 → Web/PDA 启动 → 健康检查 → 守护监测的 6 阶段流程已在测试中成功运行（虽然最终因 schema 不匹配失败）

## 5. 方案 A 实施失败的诚实复盘

### 5.1 原始计划

按推荐方案 A：使用现有 SQL Server 数据库（192.168.1.237:WaterMeterDB，已确认有 22 张表+真实数据），用 EF Core 反向工程生成模型，替换现有 C# 模型。

### 5.2 实际遇到的困难

| 预期 | 实际 | 原因 |
|------|------|------|
| EF Core 反向工程生成模型 | ✅ 成功生成 23 个文件 | 顺利 |
| 用新模型替换旧模型 | ⚠️ 命名空间冲突 | 旧代码引用不存在的类型 |
| 加 `[Column]` 属性映射 | ⚠️ 大量字段名不匹配 | C# 习惯命名 vs SQL Server 实际列名 |
| 修复 Services 引用 | ❌ 引入 200+ 新错误 | enum cast、int?→int、navigation properties 等 |
| 修复 Pages 引用 | ❌ 同样的问题 | 大面积破坏 Admin 项目 |
| 修复 Controllers | ❌ ApiResponse.Success 只读等 | API 模式差异 |

### 5.3 投入产出分析

| 阶段 | 投入 | 收益 |
|------|------|------|
| EF Core 反向工程 | 5 分钟 | ✅ 完整 SQL Server schema 文档 |
| 替换 Models + 加 Column 映射 | 30 分钟 | ✅ 字段名与 C# 习惯对齐 |
| 修复 Shared 项目 | 1 小时 | ⚠️ 从 200+ 错误降至 80 错误 |
| 修复 Api 项目 | 1 小时 | ⚠️ 仍有 20+ 错误 |
| 修复 Admin 项目 | 未完成 | ❌ 100+ 错误，放弃 |
| **总计** | **~3 小时** | **编译未通过，决定回滚** |

### 5.4 关键教训

> **"文档先行"是双刃剑**：当文档已升级到 v2.12.36 但代码还在初始骨架时，简单的"补齐"会立即暴露**整个项目是不完整骨架**的事实——这比文档落后于代码更难修复。

> **建议**：下次开发时，应该**先让代码能够编译**（哪怕只编译一个 Hello World），然后**逐个 Models/Services/Pages 增量补齐**，而不是用大规模替换。

## 8. 附录：本次会话关键决策记录

### 8.1 已验证为正确的决策

1. ✅ **使用 Windows DPAPI**（不是 MD5）做数据库连接串加密
2. ✅ **使用 BackgroundService**（不是 IHostedService）做后台任务
3. ✅ **使用 EF Core 反向工程**生成 SQL Server 模型
4. ✅ **托盘先于服务启动**的 6 阶段流程
5. ✅ **使用 `[Column]` 特性**做 C# 习惯命名到 SQL Server 列名的映射

### 8.2 已知存在的反模式

1. ⚠️ EF Core 导航属性跨层使用会导致 schema 假设问题（`Include(u => u.Employee)`）
2. ⚠️ sed 批量替换是"高风险操作"，应配合 Git 备份使用
3. ⚠️ Scaffolded 模型需要 `[Column]` 特性桥接 C# 习惯命名

### 8.3 实施过程中发现的隐藏 Bug

1. SysUser 表 5 次失败后自动锁定（设计上没有解锁界面）
2. C# 模型 `IsActive` 字段是 `new bool`（遮蔽基类）
3. `IHostedService.StartAsync` 会阻塞 Kestrel 绑定端口（应改用 `BackgroundService`）
4. 托盘进程硬编码端口（与配置文件不一致）
