# 128 — 退房联动清理房号床位（v2.13.77）

> **结论**：✅ **v2.13.77 修复退房数据一致性 BUG**：退房时同时清空 `SysEmployee.DormCode + BedNo + ResidenceStatusId`；入住时同步写入 BedNo；Dorm 端 CurrentCount + 已入住人员列表由派生查询实时联动（无需 schema 迁移）。

## 一、背景与目标

### 1.1 用户反馈（2026-07-21）

> *"在任务页面中进行退房操作确认后，则将该员工的人员清单对应员工记录的房号/床位进行清理相关信息，以及住宿档案中的对应房号/床位进行相应的处理"*

### 1.2 审计发现的数据一致性问题

| 检查项 | 当前实现 | 问题 | v2.13.77 修复 |
|--------|---------|------|--------------|
| `SysEmployee.DormCode` 退房清空 | ✅ v2.11.18 已实现 | — | — |
| `SysEmployee.ResidenceStatusId` 退房设 2 | ✅ v2.11.20 已实现 | — | — |
| **`SysEmployee.BedNo` 退房清空** | ❌ **未清空** | 人员清单床位列残留旧床位号 | ✅ 新增清空 |
| **`SysEmployee.BedNo` 入住写入** | ❌ 入住只写 DormBooking.BedNo | SysEmployee.BedNo 永远为 NULL | ✅ 新增写入 |
| `CheckInAsync` 走 SyncEmployee 统一入口 | ❌ 直接 `employee.DormCode=...` | 绕过统一方法，漏联动字段 | ✅ 改为 SyncEmployeeDormCodeAsync |
| `Dorm.CurrentCount` 自动联动 | ✅ 派生查询 `_db.DormBookings.Count(b.Status==2)` | 无需修改（设计如此） | — |
| `Dorm.已入住人员列表` 自动联动 | ✅ 派生查询 `Status==2 && DormCode==X` | 无需修改 | — |

### 1.3 单一数据源原则

**设计选择 — Dorm 端不存储 Occupancy**：
- `Dorm.CurrentOccupancy` / `Dorm.OccupiedBeds` 字段**不新增**
- 全部通过 `DormBooking.Status=2 && DormCode=X` 派生查询实时计算
- **理由**：避免「显式字段 vs SysEmployee.DormCode」的不一致风险；现有 DashboardService / DormsController / Dorms/Index/DormService 已是派生计算

## 二、详细实现

### 2.1 核心修复：SyncEmployeeDormCodeAsync 扩展 bedNo 参数

**位置**：`DormManage.Shared/Services/BookingService.cs` line 782-829

```csharp
/// v2.13.77 修订：扩展 bedNo 参数，退房时同时清空 BedNo
private async Task SyncEmployeeDormCodeAsync(int employeeId, string? dormCode, string registrar, string operation, int? bedNo = null)
{
    try
    {
        var employee = await _db.Employees.FindAsync(employeeId);
        if (employee == null) return;

        if (dormCode != null)
        {
            // 入住/撤销退房 → 同步更新 dormCode / BedNo / 住宿状态=LODGED
            var changed = false;
            if (employee.DormCode != dormCode) { employee.DormCode = dormCode; changed = true; }
            if (bedNo.HasValue && employee.BedNo != bedNo.Value) { employee.BedNo = bedNo.Value; changed = true; }
            if (employee.ResidenceStatusId != 1) { employee.ResidenceStatusId = 1; changed = true; }
            if (changed) _db.Employees.Update(employee);
        }
        else
        {
            // 退房/撤销入住 → 清空 dormCode / BedNo / 住宿状态=NOT_LODGED
            // v2.13.77 P0 修复：必须同时清空 BedNo，否则人员清单床位列残留旧床位号
            if (employee.DormCode != null || employee.BedNo != null || employee.ResidenceStatusId != 2)
            {
                employee.DormCode = null;
                employee.BedNo = null;  // v2.13.77 新增：清空床位号
                employee.ResidenceStatusId = 2;
                _db.Employees.Update(employee);
            }
        }
    }
    catch (Exception ex)
    {
        Console.WriteLine($"[v2.13.77 SyncEmployeeDormCode ERROR] {operation}: EmployeeId={employeeId}, Error={ex.Message}");
    }
}
```

**之后**（v2.13.77 — 走统一入口）：

## 三、数据流总览

### 3.1 入住流程（CheckInAsync）

```
用户提交 CheckIn 表单
       ↓
1. BookingService.CheckInAsync
   - 创建 DormBooking 记录
   - Booking.BedNo = activeCount (e.g., 3)
   - Booking.Status = 2 (Staying)
       ↓
2. SyncEmployeeDormCodeAsync(empId, dormCode, reg, "入住办理", bedNo: 3)
   - SysEmployee.DormCode = "D-301"
   - SysEmployee.BedNo = 3              ← v2.13.77 新增
   - SysEmployee.ResidenceStatusId = 1 (LODGED)
       ↓
3. 住宿档案 Dorms/Details 派生查询
   - CurrentCount: COUNT(Booking WHERE DormCode=D-301 AND Status=2)  ← +1
   - 已入住人员列表: 包含该员工 + BedNo=3
       ↓
4. 首页 KPI 派生查询
   - ResidentCount: COUNT(SysEmployee WHERE DormCode IS NOT NULL)  ← +1
```


## 五、关键决策与权衡

| 决策 | 理由 |
|------|------|
| **Dorm 端不加 CurrentOccupancy / OccupiedBeds 字段** | 现有 4 处派生查询已实时联动；schema 迁移成本 + 数据不一致风险 |
| **bedNo 用可选参数** | 向后兼容：旧调用代码 `SyncEmployeeDormCodeAsync(empId, code, reg, op)` 仍能工作（bedNo=null 不写 SysEmployee.BedNo） |
| **CheckInAsync 改为走 SyncEmployee 统一入口** | 修旧路径绕过导致 BedNo 永远为 NULL 的 BUG；统一架构减少未来的字段遗漏 |
| **派生查询 vs 显式字段权衡** | 单一数据源原则 > 性能优化（200~500 住宿规模无压力） |

## 八、核心教训

1. **数据一致性是分层责任**：单点（SysEmployee.DormCode）的修改必须联动所有依赖字段（BedNo / ResidenceStatusId）；不能假设「我只改一个字段就够了」
2. **统一入口优于散落赋值**：CheckInAsync 之前直接 `employee.DormCode=...` 绕过 SyncEmployee 是 BUG 温床；统一入口 + 必填参数才能保证未来新增字段时不会漏联动
3. **派生查询 > 显式冗余字段**：避免「字段 A vs 字段 B」的不一致；数据库范式 vs 性能权衡的经典场景
4. **关联修改务必审计完整链路**：v2.13.24 引入了 Booking.BedNo 但忘了同步 SysEmployee.BedNo；v2.13.77 修复是「迟到 1 个月」的数据一致性修正
