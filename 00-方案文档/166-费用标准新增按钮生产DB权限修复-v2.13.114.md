## 二、根本原因

### 2.1 双重失败链

v2.13.108 修复 + v2.13.110 新增权限时使用 **硬编码 ID + IDENTITY_INSERT** 模式：

```sql
-- v2.13.108 设计的「正确」SQL
SET IDENTITY_INSERT [dbo].[SysRolePermission] ON;
IF NOT EXISTS (SELECT 1 FROM [dbo].[SysRolePermission] WHERE Id = 62)
INSERT INTO [dbo].[SysRolePermission] ([Id],[RoleId],[PermissionId],[CreatedAt])
VALUES (62, 1, 41, '2026-07-22');
SET IDENTITY_INSERT [dbo].[SysRolePermission] OFF;
```

**这个 SQL 在生产 DB 上必然失败**，原因：

1. **`SysRolePermission.Id` 是 SQL Server `INT IDENTITY(1,1)` 列**
2. **生产 DB 已累积到 Id=184+**（多次历史 INSERT 留下了空隙 + 新分配）
3. **`Id=62` 早已被某条记录占用**（RoleId=9 访客 → PermissionId=1 home:view）
4. **INSERT (62, 1, 41) → PK 唯一约束违反** → 抛异常
5. **v2.13.103 单条 try/catch 模式** 静默吞掉异常 + 输出 WARNING 日志
6. **用户感知不到** → admin 永远拿不到 `billingstandard:add` 权限
7. **PageHeader.HasPerm("billingstandard:add") = false** → 按钮不显示

### 2.2 v2.13.108 IDENTITY_INSERT 修复的盲点

v2.13.108 解决了 **「IDENTITY 列不能 INSERT 显式 Id」** 的问题（这是 SQL Server 的硬限制）。

但 v2.13.108 没解决 **「即使能 INSERT 显式 Id，Id 也可能与现有 PK 冲突」** 的问题。

**生产 DB 是动态演化的**：从 v2.13.18 到 v2.13.113 共 100+ 个版本累积，硬编码 Id=58/59/60/61/62 早就被新生成的数据占用了。

### 2.3 与 v2.13.108 修复的对称失败模式

| 版本 | 错误假设 | 实际生产现象 |
|------|---------|-------------|
| v2.13.108 | "SysPermission/SysRolePermission.Id 是 IDENTITY 列，不能 INSERT 显式 Id → 加 SET IDENTITY_INSERT ON 即可" | Id=37/38/39/40 SysPermission 全部成功（生产 Id 还没占），但 SysRolePermission.Id=58/59/60/61 至少 Id=60/61 部分冲突 |
| v2.13.110 | "v2.13.108 修复模式扩展到 Id=41/62" | Id=41 SysPermission 成功（生产 Id 未占），但 Id=62 SysRolePermission **100% 冲突**（已被 RoleId=9 占） |
| **v2.13.114** | "**永远不要硬编码 Id** —— 让 IDENTITY 自动分配，按业务主键 (RoleId, PermissionCode) 唯一性判断" | ✅ 完全幂等，零冲突 |

## 三、修复方案

### 3.1 核心思路

**SysPermission 部分**：保留硬编码 Id（因为 EF Core `HasData()` 已固定 Id=37/38/39/40/41，且生产 DB 冲突概率极低）

**SysRolePermission 部分**：**完全去掉硬编码 Id**，改为「按 (RoleId, PermissionCode) JOIN SysPermission 唯一性判断」幂等模式。

```sql
-- ❌ v2.13.110 旧模式（生产 DB 必失败）
SET IDENTITY_INSERT [dbo].[SysRolePermission] ON;
INSERT INTO [dbo].[SysRolePermission] ([Id],[RoleId],[PermissionId],[CreatedAt])
VALUES (62, 1, 41, '2026-07-22');   -- Id=62 必冲突
SET IDENTITY_INSERT [dbo].[SysRolePermission] OFF;

-- ✅ v2.13.114 新模式（生产 DB 幂等）
IF NOT EXISTS (
    SELECT 1 FROM [dbo].[SysRolePermission] rp
    INNER JOIN [dbo].[SysPermission] sp ON rp.PermissionId = sp.Id
    WHERE rp.RoleId = 1 AND sp.PermissionCode = N'billingstandard:add'
)
    INSERT INTO [dbo].[SysRolePermission] ([RoleId],[PermissionId],[CreatedAt])
    SELECT 1, Id, '2026-07-23' FROM [dbo].[SysPermission]
    WHERE PermissionCode = N'billingstandard:add';
```

## 六、核心教训

| # | 教训 | 适用场景 |
|---|------|---------|
| 1 | **IDENTITY 列永远不要硬编码 Id**：除非有 HasData 等元数据保证 Id 永久可用 | 所有 SysXxx 表（SysPermission/SysRolePermission/SysRole 等） |
| 2 | **业务主键优于物理主键**：用 (RoleId, PermissionCode) 替代 Id 唯一性判断 | 所有 FK 关联表 |
| 3 | **try/catch 静默吞掉是 BUG 温床**：每次启动迁移必须验证最终一致性 + 缺失项日志 | 所有启动迁移代码 |
| 4 | **生产 DB 状态不可预测**：从 v2.13.18 到 v2.13.113 共 100+ 版本，硬编码 Id 必冲突 | 所有 IDENTITY 列 |
| 5 | **手动 SQL 兜底必须幂等**：用 IF NOT EXISTS 守卫 + 不指定 Id，让 IDENTITY 自动分配 | 所有手动 seed SQL |
