## 二、唯一性语义（全局唯一）

设备档案每条记录含 3 个设备ID：**电表ID / 冷水表ID / 热水表ID**。三者**全局唯一**，两重约束：

| 约束 | 含义 | 示例（拒绝） |
|------|------|--------------|
| **① 同一记录内互斥** | 电表ID ≠ 冷水表ID ≠ 热水表ID | 一条记录 电表ID=冷水表ID=`E009` → 拒绝 |
| **② 跨记录全局唯一** | 任一 ID 不与其它任何记录的任一字段重复 | A 记录电表ID=`E001`，B 记录冷水表ID 也填 `E001` → 拒绝 |

- **空值（NULL/空串）不参与判断**：某间住宿可只装电表不装水表。
- 用户原话「禁止多个记录填入相同一个设备ID」= 全局唯一（取最严格语义）。

### Service 层核心代码（已就绪，本次保留）

```csharp
private async Task<string?> CheckDeviceIdUniqueAsync(
    string? electricId, string? coldId, string? hotId, int? excludeId = null)
{
    // ① 同记录内互查：3 个 ID 互相不能重复
    var idsInRecord = new[] {
        (label: "电表ID", val: electricId?.Trim()),
        (label: "冷水表ID", val: coldId?.Trim()),
        (label: "热水表ID", val: hotId?.Trim())
    }.Where(x => !string.IsNullOrEmpty(x.val)).ToList();
    foreach (var g in idsInRecord.GroupBy(x => x.val!.ToLowerInvariant()).Where(g => g.Count() > 1))
        return $"同一记录内设备 ID 重复：{string.Join(" 和 ", g.Select(x => x.label))} 都为 '{g.Key}'";

    // ② 跨表互查：与其它记录的任一字段不重复
    foreach (var (label, val) in idsInRecord)
    {
        var query = _db.DormMeters.Where(m =>
            m.ElectricMeterId == val || m.ColdWaterMeterId == val || m.HotWaterMeterId == val);
        if (excludeId.HasValue) query = query.Where(m => m.Id != excludeId.Value);
        var conflict = await query.Include(m => m.Dorm).FirstOrDefaultAsync();
        if (conflict != null)
            return $"{label} '{val}' 已被房号 {conflict.Dorm?.DormCode ?? $"Id={conflict.DormId}"} 占用（设备档案 #{conflict.Id}）";
    }
    return null;
}
```

## 四、DB 过滤索引边界说明（重要）

过滤唯一索引 `WHERE col IS NOT NULL` 只能表达「**同列内唯一**」，且允许多行 NULL：

- ✅ 能拦：两条记录的 **电表ID** 相同（同列重复）；
- ❌ 拦不到：A 记录 **电表ID** 与 B 记录 **冷水ID** 相同（跨列全局重复）——这部分**仅 Service 层**拦截。

**结论**：DB 索引是「同列重复」的兜底，主约束始终是 Service 层 `CheckDeviceIdUniqueAsync`。SQL Server 不支持跨列的复合唯一约束，跨列唯一逻辑必须留在应用层。

## 五、迁移安全性（guarded）

`03_Migration_v2.13.168_DeviceIdUnique.sql` 与 `DatabaseInitializer.cs` 启动自愈逻辑对每列**双重 guard**：

1. **该列存在重复值** → 跳过建索引 + `PRINT` 警告列出重复项（**不阻断**，交人工清理后重跑）；
2. **索引已存在** → 跳过（幂等）。

生产库若已有历史重复数据，绝不会导致迁移失败或启动崩溃。

## 八、永久教训

1. **业务硬约束必须多层防御**：AJAX 直连 API 的模块，防御层为 UI + Service(API) + DB；Service 是主约束收口，DB filtered index 是兜底，两者边界（跨列 vs 同列）必须文档显式标注。
2. **filtered unique index 的能力边界**：`WHERE col IS NOT NULL` 只保证同列唯一 + 允许多行 NULL；跨列/复杂唯一逻辑（如"任一列全局唯一"）SQL Server 无法用单索引表达，必须回到应用层。
3. **建唯一索引前必须 guard 历史数据**：直接 `CREATE UNIQUE INDEX` 遇重复数据会报错中断；迁移脚本与启动自愈都要先检测重复并优雅跳过 + 打印警告，绝不阻断部署/启动。
4. **中断任务收尾要先摸清现状**：`git status` + 代码里的版本标记（`v2.13.168` 注释）比记忆更可靠——先确认「已做/未做」再补齐，避免重复实现或遗漏收尾。
