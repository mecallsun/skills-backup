# 启动路径解析修复（托盘拉起 Api/Admin「可执行文件不存在」）— v2.13.156

> **日期**：2026-07-25
> **类型**：P0 BUG 修复 + 配置健壮性提升
> **触发**：用户实测反馈「启动时提示：Api 可执行文件不存在」
> **改动文件**：`DormManage.TrayApp/Models/AppConfig.cs`（默认 2 行）+ `DormManage.TrayApp/Services/ProcessManager.cs`（`TryResolveExePath` 重写为多候选 fallback）+ `scripts/reset-tray-config.ps1`（新增 56 行一键兜底）

---

## 一、根因（双重 BUG 叠加）

### 1.1 BUG A — `AppConfig.cs` 默认值假设了错误部署布局

```csharp
// v2.13.142 起（错误）
public string ApiExecutable { get; set; } = "..\\Api\\DormManage.Api.exe";
public string AdminExecutable { get; set; } = "..\\Admin\\DormManage.Admin.exe";
```

**问题**：`..\` 假设 `publish-final/{TrayApp,Api,Admin}/` 是同级并列（v2.13.142 文档注释推断），但 `dotnet publish -o publish-final/Api` 与 `-o publish-final/TrayApp` 实际是**不同发布**——各自是独立的 publish-final 子树。用户在不同目录解压/拷贝时，`..\Api\...` 在某些布局下会失效。

### 1.2 BUG B — `ConfigService.Load()` 一旦成功反序列化就**永远用文件值**

```csharp
var loaded = JsonSerializer.Deserialize<AppConfig>(json, JsonOpts);
_current = loaded;  // ← 用户历史配置中的失效路径被永久保留
```

→ 即使代码默认值修复了，已部署的用户 `appsettings.json` 里的失效路径**永远不会自动回到新默认值**。

### 1.3 BUG C — `TryResolveExePath` 无 fallback

只尝试 1 条路径，找不到就抛 `FileNotFoundException`，无任何智能探测。

## 二、修复

### 2.1 默认值改为「相对自身目录」（`AppConfig.cs`）

```csharp
// v2.13.156 起：publish-final/TrayApp/Api/DormManage.Api.exe（同级子目录）
public string ApiExecutable { get; set; } = "Api\\DormManage.Api.exe";
public string AdminExecutable { get; set; } = "Admin\\DormManage.Admin.exe";
```

### 2.2 多候选 fallback（`ProcessManager.TryResolveExePath`）

按优先级探测 9 条候选路径，任一匹配即返回：

1. 配置原始值（相对 BaseDirectory 或绝对）
2. 相对 BaseDirectory 的 Api/Admin 子目录（当前默认）
3. 兼容 v2.13.142 旧默认（`..\Api\`）
4. 相对 BaseDirectory 父目录的 Api/Admin（dev 模式 publish-final 直接并列）
5. 当前工作目录兜底

→ **历史失效配置无需人工干预**，下次启动自动修复。

### 2.3 `scripts/reset-tray-config.ps1` 一键兜底工具

兜底脚本（用户从「移动设备拷贝 / 跨机器迁移」场景）：备份原 `appsettings.json`，自动探测 Api/Admin EXE 路径并写入新配置。**适用**托盘端的 console 报错信息足够清晰时可定位问题，但用户懒得分析时一键修复。

## 三、真机复测（3 种布局全过）

| 场景 | appsettings 中的 ApiExecutable | 结果 |
|------|-------------------------------|------|
| A. 标准布局（无 appsettings 首次启动） | 无 → 用新默认 | ✅ Api 5100 + Admin 5001 |
| B. 旧默认（v2.13.142 `..\Api\`） | `..\Api\DormManage.Api.exe` | ✅ fallback 找到正确路径 |
| C. 用户硬编码绝对路径（拷贝到 D 盘） | `D:\Totally\Wrong\Path\...` | ✅ fallback 找到正确路径 |

**关键证据**：场景 C 中日志显示 `[INFO] Api 进程已启动 PID=44768` / `Admin 进程已启动 PID=43192` —— 即使用户 `appsettings.json` 写着完全无关的 `D:\Totally\Wrong\...`，托盘依然成功启动 Api/Admin（v2.13.156 多候选兜底生效）。

## 四、永久教训

| # | 教训 |
|---|------|
| 1 | **「默认值必须反映真实部署布局」**。Code 默认与文档描述的部署结构必须严格一致，否则首次启动就会写出无效路径。 |
| 2 | **「一次性持久化默认值」是暗藏陷阱**。ConfigService 永远用文件值 → 用户一旦配置过失效路径，新默认值无效。代码默认值修复不彻底，必须配 fallback 探测才能闭环。 |
| 3 | **「路径解析必须多候选 fallback」**。任何软件发布后都可能被解压到任意位置，单一路径解析假设是脆弱的。多候选 + 自动降级是健壮性最低保证。 |
| 4 | **托盘端兜底工具必不可少**。当 Console 报错无法让用户快速自我修复时，一键恢复脚本（`reset-tray-config.ps1`）是把「工程师修」降级为「用户自己修」的关键设计。 |
