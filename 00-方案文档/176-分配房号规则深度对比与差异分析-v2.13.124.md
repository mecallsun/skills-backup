## 四、5 大差异点深度分析

### 4.1 [P0] 排序反转：空房 P2 → P4

#### 现状（v2.13.123 错误）

```csharp
.ThenByDescending(d => d.CurrentCount == 0)  // P2: 空房号优先
```

#### 问题

v2.13.112 引入的排序逻辑将"空房号"放在 P2（次高优先级），导致：
- 选员工后，**空房间总是排在已住人员房间前面**
- 即便该员工与某个已住人员**同班组**，但**不同班次**，系统也会优先推荐**空房间**
- **违反用户真实业务诉求**：用户希望保持团队稳定性（同班组聚集）

#### 修复（v2.13.124）

```csharp
.ThenByDescending(d => d.IsEmpty)  // P4: 空房间（兜底）
```

### 4.2 [P0] 排序位置调整：同班次 P3 → P2

#### 现状（v2.13.123 错误）

```csharp
.ThenBy(d => d.MainAttendanceTypeId == empAttId ? 0 : 1)  // P3: 同班次优先
```

#### 问题

"同班次"放在 P3，但实际上应该比"空房"优先：
- 同班次（作息一致）+ 不同班组 → 比空房间更适合（作息一致但有人住）
- 空房间 → 兜底（没人没作息）

#### 修复（v2.13.124）

```csharp
.ThenByDescending(d => d.IsSameAttendanceOnly)  // P2: 不同班组但同班次
```

### 4.3 [P0] "不同班次"分类缺失

#### 现状（v2.13.123 完全缺失）

v2.13.123 没有显式区分"不同班次"，所有"非同班次"的房间都被混在一起。

#### 用户诉求

> "其三是不同班次"

#### 修复（v2.13.124）

在 P3 显式区分"不同班组 + 不同班次"（即"完全陌生人"）：

```csharp
.ThenByDescending(d => d.CurrentCount > 0 && !d.IsSameAttendanceOnly)  // P3: 不同班组不同班次
```

### 4.4 [P0] MainAttendanceTypeName 字段缺失

#### 现状（v2.13.123 错误）

DormOption 仅有 `MainAttendanceTypeId`（int），没有 `MainAttendanceTypeName`（string），也没有 `AttendanceTypes: List<string>` 完整集合。

#### 问题

前端 CheckIn.cshtml 在 option 文本中只能显示"班次 ID"或完全省略，无法满足用户原话：

> "列表显示中，同时附带显示已入住人员的班组**及班次**名称"

#### 修复（v2.13.124）

新增 3 个字段：
- `MainAttendanceTypeName: string?` — 主要班次名称
- `AttendanceTypes: List<string>` — 完整班次集合（去重 + 按人数降序）
- `IsSameAttendanceOnly: int` — P2 排序权重
- `IsEmpty: int` — P4 排序权重

### 4.5 [P0] 强锁定 dormSelect 缺失

#### 现状（v2.13.123 弱提示）

#### 用户诉求

function sortAvailableDormsByPriority(list, empTeamId, empAttId) {
    return list.slice().sort((a, b) => {
        // P1: 同班组（最高权重，"有熟人"）
        const aHasTeam = empTeamId && a.teamNames && a.teamNames.length > 0
            ? TEAMS.some(t => t.id === empTeamId && a.teamNames.includes(t.name)) : false;
        const bHasTeam = empTeamId && b.teamNames && b.teamNames.length > 0
            ? TEAMS.some(t => t.id === empTeamId && b.teamNames.includes(t.name)) : false;
        if (aHasTeam !== bHasTeam) return aHasTeam ? -1 : 1;

        // P2: 不同班组但同班次（"作息一致但陌生人"）
        const aMainAtt = getMainAttendanceType(a.dormCode);
        const bMainAtt = getMainAttendanceType(b.dormCode);
        const aSameAtt = !aHasTeam && aMainAtt === empAttId && a.in宿 > 0;
        const bSameAtt = !bHasTeam && bMainAtt === empAttId && b.in宿 > 0;
        if (aSameAtt !== bSameAtt) return aSameAtt ? -1 : 1;

        // P3: 不同班组不同班次（"完全陌生人"）+ P4: 空房间（兜底）
        const aHasPeople = a.in宿 > 0;
        const bHasPeople = b.in宿 > 0;
        if (aHasPeople !== bHasPeople) return aHasPeople ? -1 : 1;

        // 字典序稳定排序
        return a.dormCode.localeCompare(b.dormCode);
    });
}

## 七、永久教训

### 7.1 "空房优先" vs "熟人优先" 业务哲学差异

| 哲学 | 业务诉求 | 适用场景 |
|------|---------|---------|
| **空房优先** | 给新人腾房 | 流动性大的住宿 |
| **熟人优先** | 同班组/同班次保持聚集 | 团队稳定性高的住宿 |

**用户的选择是"熟人优先"**：业务诉求是"保持团队稳定性"。

### 7.2 排序反转是 13 个版本未被发现

v2.13.112 引入排序逻辑 → v2.13.116 汇总为 R3 → v2.13.123 终极汇总。**13 个版本**用户未发现排序反转 BUG。

**教训**：业务硬约束（排序优先级）必须**通过用户实际场景测试**才能验证正确性，单测/集成测试无法覆盖"哲学正确性"。

### 7.3 字段名称 ≠ 显示名称

`MainAttendanceTypeId`（int）≠ `MainAttendanceTypeName`（string）。

**教训**：派生字段的"显示需求"必须在最初就规划。当前 DormOption 仅有 ID，前端需要 JOIN AttendanceType 表才能显示，违反"单一 API 返回完整可显示数据"原则。

### 7.4 校验弱提示 vs 强锁定的语义差异

| 模式 | 用户体验 | 适用 |
|------|---------|------|
| 弱提示 | 用户可继续操作 + 看到红色告警 | 信息性提示 |
| 强锁定 | 用户无法提交 + 必须先修复 | 业务硬约束 |

**用户的诉求是"解锁"语义**，应该实施强锁定模式。

### 7.5 用户原话 vs 文档实现的双向校验

| 维度 | 文档描述 | 实现描述 |
