### 2.2 Booking/Index 列表（12 列 → 13 列）

**DTO 改造**：PageModel 注入 DormDbContext + GenderMap 字典（避免 N+1）：
```csharp
public Dictionary<int, int> GenderMap { get; set; } = new();

public async Task OnGetAsync()
{
    Result = await _service.GetListAsync(...);
    if (Result?.Items != null && Result.Items.Any())
    {
        var empIds = Result.Items.Select(b => b.EmployeeId).Distinct().Where(id => id > 0).ToList();
        GenderMap = await _db.Employees
            .Where(emp => empIds.Contains(emp.Id))
            .Select(emp => new { emp.Id, emp.Gender })
            .ToDictionaryAsync(x => x.Id, x => x.Gender);
    }
}
```

## 三、性能优化

**避免 N+1 查询**：
- 列表页（Booking Index / EmployeeBilling Index / Dorms History）一律使用批量 JOIN：
  ```csharp
  var empIds = items.Select(...).Distinct().ToList();
  var genderMap = await _db.Employees.Where(emp => empIds.Contains(emp.Id))
      .Select(emp => new { emp.Id, emp.Gender })
      .ToDictionaryAsync(...);
  ```
- 单页查询量从 `O(N)` 降到 `O(1)` JOIN

**索引复用**：SysEmployee.Id 已是主键索引，无需新增。

## 五、关键决策与权衡

| 决策 | 理由 |
|------|------|
| **批量 JOIN 避免 N+1** | 列表场景下 N+1 会导致每次翻页 N 次额外查询 |
| **性别作为新列（Booking）** | 与 v2.13.83 Personnel/Index 风格一致；与姓名/工号形成「人员三要素」 |
| **性别作为 Badge 内联（CheckOut/Edit）** | 不破坏现有布局；视觉简洁 |
| **BookingListDto API 端同步** | 与 v2.13.66 Department / v2.13.47 EmployeeCode 同步策略一致 |
| **无新增字段或迁移** | Gender 字段已在 SysEmployee 表（v2.13.83 回填） |

## 七、风险与回退

### 7.1 列表列数变化（Booking/Index 12→13）

**风险**：可能影响其他依赖 Booking/Index 表格的脚本或截图工具。
**缓解**：colspan 已同步调整；列定义清晰（工号/姓名/性别/部门/...）。

### 7.2 DormDbContext 注入到 Booking/Index

**风险**：原 IndexModel 只注入 IBookingService，新增 DormDbContext 可能破坏现有 DDD 分层。
**缓解**：DormDbContext 已是 Admin 项目通用依赖（PageModel 中频繁使用）；不影响业务边界。
