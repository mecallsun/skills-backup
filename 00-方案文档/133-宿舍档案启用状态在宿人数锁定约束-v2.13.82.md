# 133 — 住宿档案「启用状态」在宿人数锁定约束（v2.13.82）

> **结论**：✅ **v2.13.82 完成住宿档案「启用该住宿」复选框的「在宿人数 > 0 时锁定」业务约束**——三层防御（UI 禁用 + PageModel POST 校验 + API 拒绝），确保有在宿员工的住宿不会被误停用，避免在宿员工失去 Dorm 关联。

## 一、用户反馈（2026-07-21）

> *"增加 住宿档案 编辑 或修改 启用档案 状态的 约束，当住宿有在宿人数大于0时，则禁止 将 启用住宿 状态的勾选 状态 取消，即锁定勾选状态复选控件，请更新相关规则 逻辑，全面理解 更新程序"*

**业务背景**：
- 当前 `Dorm.IsActive` 是布尔标志位，**无任何业务约束**
- 管理员在「住宿档案 → 编辑」页面**可以直接取消勾选**「启用该住宿」复选框
- 当住宿 `CurrentCount > 0`（有在宿员工，`Status = BookingStatus.Staying = 2`）时，停用住宿会导致：
  - 抄表分配隐藏该住宿（Index 筛选 IsActive=true 排除）
  - 新办理入住找不到可用住宿
  - 在宿员工失去对应的 Dorm 关联（DormBooking.DormCode 仍存在，但 Dorm 实体被标记 IsActive=false）
- **必须三重防御**：UI 禁用复选框 + PageModel POST 校验拒绝 + API 拒绝

## 三、目标

实现「启用住宿」复选框的**业务规则约束**：当住宿当前在宿人数 `CurrentCount > 0` 时：

1. **UI 层**：复选框 `disabled="disabled"` + 显示锁定提示（锁图标 + 在宿人数 badge + 警告 alert）
2. **PageModel 层**：`OnPostAsync` 校验拒绝，返回带 ModelState 错误的 Page（HTTP 200 + 重新渲染锁定提示）
3. **API 层**：`UpdateDorm` 校验拒绝，返回 `DORM_HAS_RESIDENTS` 业务错误（HTTP 200 + `success=false`）

### 5.2 `DormManage.Admin/Pages/Dorms/Edit.cshtml.cs`（PageModel 修改）

**新增字段**：
```csharp
/// <summary>v2.13.82 业务约束：当前在宿人数（动态计算）</summary>
public int CurrentCount { get; set; }

/// <summary>v2.13.82 业务约束：CurrentCount > 0 时锁定 IsActive 复选框</summary>
public bool IsActiveLocked => CurrentCount > 0;

/// <summary>v2.13.82 业务约束：原始 IsActive 值（OnPost 校验失败的回显）</summary>
public bool IsActiveOriginal { get; set; }
```

**OnGetAsync 增加 CurrentCount 查询**：
```csharp
public async Task<IActionResult> OnGetAsync(int id)
{
    var dorm = await _db.Dorms.FindAsync(id);
    if (dorm == null) return NotFound();

    // v2.13.82 业务约束：当前在宿人数 > 0 时锁定 IsActive
    CurrentCount = await _db.DormBookings
        .CountAsync(b => b.DormCode == dorm.DormCode && b.Status == BookingStatus.Staying);

    Dorm = new DormEditDto { /* ...原有字段... */ };
    IsActiveOriginal = dorm.IsActive;

    await LoadBasicsAsync();
    return Page();
}
```

**OnPostAsync 顶部提前计算 CurrentCount + 业务约束校验**：
```csharp
public async Task<IActionResult> OnPostAsync()
{
    // v2.13.82 即便 ModelState 失效也要重新计算 CurrentCount 以便锁定提示继续显示
    if (await _db.Dorms.FindAsync(Dorm.Id) is { } dormForCount)
    {
        CurrentCount = await _db.DormBookings
            .CountAsync(b => b.DormCode == dormForCount.DormCode && b.Status == BookingStatus.Staying);
    }

    if (!ModelState.IsValid)
    {
        await LoadBasicsAsync();
        return Page();
    }

    var dorm = await _db.Dorms.FindAsync(Dorm.Id);
    if (dorm == null) return NotFound();

    // v2.13.82 业务约束：在宿人数 > 0 时禁止取消启用
    // 锁定条件：当前 dorm.IsActive=true 且 表单提交 Dorm.IsActive=false 且 CurrentCount > 0
    if (dorm.IsActive && !Dorm.IsActive && CurrentCount > 0)
    {
        IsActiveOriginal = dorm.IsActive;
        ModelState.AddModelError("Dorm.IsActive",
            $"该住宿当前在宿 {CurrentCount} 人，禁止停用。请先办理所有人员退宿手续后再操作。");
        await LoadBasicsAsync();
        return Page();
    }

    // ... 原有保存逻辑
}
```

**关键点**：
- 三层防御：(1) UI 禁用；(2) PageModel 校验；(3) 不修改数据库直到 ModelState 合法
- 即使前端被绕过（手动 POST `IsActive=false`），PageModel 仍拒绝
- 校验失败的场景**严格限定**为「当前启用 + 试图取消启用 + 在宿 > 0」——已停用的住宿再次保存仍然允许
- 提前计算 CurrentCount（即使 ModelState 失效），确保重新渲染时锁定提示继续生效

### 5.3 `DormManage.Api/Controllers/Dorms/DormsController.cs`（API 修改）

**UpdateDorm (line 163-218) 增加校验**：
```csharp
[HttpPut("{id}")]
public async Task<ApiResponse<DormDto>> UpdateDorm(int id, [FromBody] DormUpdateRequest request)
{
    var dorm = await _db.Dorms.FindAsync(id);
    if (dorm == null)
        return ApiResponse<DormDto>.Fail("NOT_FOUND", "住宿不存在");

    if (await _db.Dorms.AnyAsync(d => d.DormCode == request.DormCode && d.Id != id))
        return ApiResponse<DormDto>.Fail("CODE_EXISTS", "该住宿号已存在");

    // v2.13.82 业务约束：在宿人数 > 0 时禁止停用住宿（优先于容量校验）
    // 锁定条件：当前 dorm.IsActive=true 且 请求 IsActive=false 且 CurrentCount > 0
    var currentStaying = await _db.DormBookings
        .CountAsync(b => b.DormCode == dorm.DormCode && b.Status == 2);
    if (dorm.IsActive && !request.IsActive && currentStaying > 0)
    {
        return ApiResponse<DormDto>.Fail(
            "DORM_HAS_RESIDENTS",
            $"该住宿当前在宿 {currentStaying} 人，禁止停用。请先办理所有人员退宿手续后再操作。");
    }

    // v2.13.12: 容量变更约束（保留）
    if (request.Capacity < currentStaying)
        return ApiResponse<DormDto>.Fail("CAPACITY_EXCEEDED", $"当前入住 {currentStaying} 人，容量不能少于入住人数");

    // ... 原有保存逻辑
}
```

**关键点**：
- 校验放在容量校验之前（先校验业务硬约束，再校验软约束）
- 错误码 `DORM_HAS_RESIDENTS` 与现有 `CAPACITY_EXCEEDED` / `HAS_BOOKINGS` 风格一致
- PUT `/api/dorms/{id}` 路径直接拒绝 `IsActive=false`，PDA/集成调用即使绕过 UI 也会收到 400 + 业务错误

## 七、关键决策与权衡

| 决策 | 理由 |
|------|------|
| **三层防御（UI + PageModel + API）** | UI 可被绕过（手动 POST）；PageModel 校验保护默认路径；API 校验保护 PDA/集成调用 |
| **锁定条件 = 当前 IsActive=true + 试图取消 + CurrentCount>0** | 不影响「停用 → 启用」流程；不影响「已停用状态保存其他字段」 |
| **不修改 DormService.cs** | 该约束作用于编辑路径，与现有 `UpdateCapacityAsync` 是正交逻辑。共享校验函数可后续 v2.13.83 重构 |
| **不锁定 Create 页面** | 新住宿 CurrentCount 必为 0 |
| **保留 `asp-for` 自动 hidden 字段** | 禁用 checkbox 时仍需提交 IsActive=true，避免值丢失 |
| **PageModel 失败后保留 CurrentCount + IsActiveOriginal** | 重新渲染页面时锁定提示继续生效 |
| **不修改 Dorm.cs 实体** | IsActive 字段已存在；CurrentCount 是动态计算字段，不存表 |
| **不引入「强制停用」按钮** | 绕过业务约束会带来数据不一致风险；如需紧急停用，先在「办理登记」完成所有人员退宿 |

## 十二、核心教训

1. **「软约束」也要三重防御**：与硬约束（如 `Required`）不同，业务规则（如「有在宿人数时不能停用」）必须 UI + PageModel + API 三层都实现
2. **CurrentCount 是动态字段不是表列**：很多人会误以为 `Dorm.CurrentCount` 是 Dorm 表的一列，实际是 LINQ 动态计算。任何 Dorm 约束都必须先理解这一点
3. **`asp-for` checkbox 的 hidden 字段保护**：禁用 checkbox 时如果移除了 hidden 字段，提交时 IsActive 会变成默认值 `false`，反而"取消"了启用状态。v2.13.62 类似 BUG（费用标准 `IsActive`）已经在 CLAUDE.md 记录教训
4. **PageModel 校验失败时保留辅助数据**：如 CurrentCount 必须在 OnPost 顶部重新计算，否则 ModelState 错误 + return Page() 时锁定提示会消失
5. **PUT /api/dorms/{id} 是公开端点**：PDA / 第三方集成都可能调用，仅靠 UI 校验无法防御，必须在 API Controller 加业务规则
