## 一、问题

**用户 3 次反馈同一问题**（v2.13.97 → v2.13.100 → v2.13.101 → v2.13.102）：
> "请检查 在 权限矩阵 中，在角色定义 的 权限分配 中 人员清单  权限清单 没有显示 '新建' 按键的权限项？ 为什么? 勾选 的权限控制项没有生效？"

**v2.13.100/101 已修复代码层 + 启动日志，但用户仍感知不到**：
- v2.13.100 修复 `DatabaseInitializer.MigrateFieldPermissionAsync` 中 SysPermission Id=40 (`personnel:add`) + SysRolePermission Id=61 seed 缺失问题
- v2.13.101 修复 `MigrateFieldPermissionAsync` 末尾追加完整性验证日志
- **但用户只看 UI 不会看启动日志** → 一直以为"代码没改"

## 二、根因（5 部署态路径）

| # | 可能原因 | 概率 |
|---|---------|------|
| 1 | Admin 未重启 → `DatabaseInitializer.InitializeAsync` 未执行 | 高 |
| 2 | 数据库文件不一致：Admin 连接了一份 DB，TrayApp 连接了另一份 | 高 |
| 3 | `ExecuteSqlRawAsync` 静默失败（如外键约束、列缺失）但 try/catch 吞错 | 中 |
| 4 | 浏览器缓存未硬刷 | 中 |
| 5 | SysPermission.Id=40 的 ParentId 被手工 SQL 误改为非 9 | 低 |

**共性**：所有失败场景下，用户在 UI 上**看不到任何提示**，只能反复找 Claude 反馈。

## 三、修复（v2.13.102）— 三层防护完整化

### 3.1 服务层 — `DatabaseInitializer.CheckSeedIntegrityAsync`

**新文件位置**：`DormManage.Shared/Services/DatabaseInitializer.cs`（在 ComputeSha256 之后插入）

```csharp
public static async Task<SeedIntegrityReport> CheckSeedIntegrityAsync(
    DormDbContext db, CancellationToken ct = default)
{
    var requiredPermIds = new[] { 37, 38, 39, 40 };
    var requiredRpIds   = new[] { 58, 59, 60, 61 };
    const int expectedFieldPermCount = 5;

    // 三段独立 try/catch — 任一查询失败不阻塞整体
    var presentPerms = new List<int>();
    var presentRps = new List<int>();
    int fieldPermCount = 0;
    try { presentPerms = await db.Database.SqlQueryRaw<int>(
        "SELECT Id FROM SysPermission WHERE Id IN (37,38,39,40)").ToListAsync(ct); } catch {}
    try { presentRps = await db.Database.SqlQueryRaw<int>(
        "SELECT Id FROM SysRolePermission WHERE Id IN (58,59,60,61)").ToListAsync(ct); } catch {}
    try { fieldPermCount = await db.SysFieldPermissions.CountAsync(ct); } catch {}

    var missingPerms = requiredPermIds.Except(presentPerms).ToList();
    var missingRps   = requiredRpIds.Except(presentRps).ToList();
    var ok = missingPerms.Count == 0 && missingRps.Count == 0 && fieldPermCount >= expectedFieldPermCount;

    return new SeedIntegrityReport { /* ... */ };
}
```

**同时把 `MigrateFieldPermissionAsync` 从 `private static` 改为 `public static`**，让 banner handler 可直接调用实现"一键修复"。

### 3.2 API 层 — `GET /api/v1/system/seed-integrity`

**新端点**：`DormManage.Api/Controllers/System/SystemController.cs`

```csharp
[HttpGet("seed-integrity")]
public async Task<ApiResponse<SeedIntegrityReport>> CheckSeedIntegrity()
{
    try
    {
        var report = await DatabaseInitializer.CheckSeedIntegrityAsync(_db);
        return ApiResponse<SeedIntegrityReport>.Ok(report, report.Ok ? "完整性检查通过" : report.Summary);
    }
    catch (Exception ex)
    {
        _logger.LogWarning(ex, "[v2.13.102] seed 完整性查询异常");
        return ApiResponse<SeedIntegrityReport>.Fail("INTEGRITY_CHECK_FAIL", $"完整性查询异常：{ex.Message}");
    }
}
```

### 3.3 UI 层 — 三处协作

#### A. `RolePanelPartial.cs` — 新增字段 + 2 handler

```csharp
public SeedIntegrityReport? SeedIntegrity { get; set; }

public async Task LoadRolePanelAsync()
{

    try { SeedIntegrity = await DatabaseInitializer.CheckSeedIntegrityAsync(_db); }
    catch { SeedIntegrity = null; /* 不阻塞 Tab 渲染 */ }

// 一键修复
public async Task<IActionResult> OnPostRoleSeedRepairAsync()
{
    var logger = HttpContext.RequestServices.GetRequiredService<ILoggerFactory>().CreateLogger("SeedRepair");
    var migrated = await DatabaseInitializer.MigrateFieldPermissionAsync(_db, logger, CancellationToken.None);
    var report = await DatabaseInitializer.CheckSeedIntegrityAsync(_db, CancellationToken.None);
    return new JsonResult(new {
        success = migrated && report.Ok,
        message = report.Ok ? "seed 完整性修复成功" : $"修复完成但仍有缺失：{...}"
    });
}
```

## 七、决策与权衡

| 决策 | 理由 |
|------|------|
| **复用 v2.13.101 验证 SQL 但独立方法** | 不破坏现有 MigrateFieldPermissionAsync 行为；分离"运行检查"与"启动迁移"职责 |
| **banner 仅在 permMatrixModal 显示** | 用户复现路径必经此 Modal；避免污染整个 Settings 页 |
| **三段式 UX：banner + 重新检查 + 一键修复** | 用户从「看」到「主动检查」到「立即修复」，无需重启 Admin 闭环 |
| **`MigrateFieldPermissionAsync` private → public** | 让 banner handler 直接调用；迁移逻辑单一真源 |
| **缺失项中文标签写死映射** | 7 个 Id 数量固定，写死比 DB 反查 PermissionCode 更高效 |
| **不动 SysPermission.HasData** | HasData 不迁移是真因，但项目无 EF Migrations 机制——保持现状 |
| **视觉风格选 nested card 不用 alert** | L213 隐私字段权限 nested card 同 Modal 内已有参照；缺失项需列详细 + 操作按钮，alert 容纳不下 |
| **不删除 v2.13.101 启动日志** | 启动日志 + UI banner + 一键修复 三层防护，运维和用户都能看到/操作 |

## 八、风险与回退

| 风险 | 缓解 |
|------|------|
| `CheckSeedIntegrityAsync` 在生产大库上查询慢 | 4 行/8 行的 SqlQueryRaw，毫秒级 |
| Banner 干扰现有 UX | 仅 Modal 顶部、nested card 模式，缺则不显示 |
| AJAX 调用频繁 | 仅在用户点"重新检查"按钮触发，无轮询 |
| `MigrateFieldPermissionAsync` 暴露为 public 后被乱用 | XML doc 注释明确"仅 DatabaseInitializer 调用 + banner handler 调用" |
| 一键修复 POST 在生产环境误触发 | confirm 对话框二次确认；MigrateFieldPermissionAsync 全 idempotent |

## 九、教训（v2.13.102）

1. **「日志可见化」≠「用户可见化」**：v2.13.101 启动日志对运维有效，但**普通用户不看日志**——必须在 UI 层面同步暴露
2. **三层防护要齐备**：(1) 启动日志（运维） (2) UI banner（用户） (3) 一键修复（用户主动操作）——v2.13.100/101 缺后两层
3. **「权限矩阵」要可观测**：权限/菜单/数据 seed 是系统运行的前提，必须有 UI 自检通道
4. **「一键修复」避免重启**：用户不愿意为 seed 缺失重启 Admin；提供 idempotent 修复 handler 是关键 UX
