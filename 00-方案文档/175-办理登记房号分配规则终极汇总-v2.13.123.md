### 3.1 R1：选员工立即显示档案（v2.13.113）

#### 定义

选中员工后 `selectEmp(emp)` 立即渲染 `emp-info-card`，8 字段全部从 API `EmployeeSearchResult` DTO 映射。

#### 字段对照表

| 字段 | 数据源 | 渲染方式 | v2.13.113 修复点 |
|------|--------|---------|-----------------|
| 工号 | `emp.employeeCode` | 纯文本 | — |
| 姓名 | `emp.realName` | 纯文本 | — |
| 性别 | `emp.gender`（1=男 2=女 0=未知）| Badge（bi-gender 图标）| v2.13.86 |

| 类型 | `emp.employeeTypeName`（FK `EmployeeType.Name`）| 纯文本 | — |

### 3.2 R2：三层性别过滤（v2.13.84）

#### 定义

`BookingService.GetAvailableDormsAsync` 返回的下拉候选项必须满足以下三层过滤：

| 层级 | 规则 | 拒绝条件 |
|------|------|---------|
| **L1 余量** | `available = capacity − currentIn宿 − reserved > 0` | `available <= 0` 直接 `continue` |
| **L2 性别** | 见下方性别过滤矩阵 | 见矩阵 |
| **L3 完全空** | 允许任何性别入住空房间 | — |

#### 性别过滤矩阵

| 员工 Gender | 宿舍当前在宿 | 是否可选 | 业务原因 |
|-----------|------------|---------|---------|
| **1（男）** | 总人数 = 0（空房）| ✅ 放行 | 任何人都可进空房 |
| **1（男）** | MaleCount > 0, FemaleCount = 0 | ✅ 同性别 OK | — |
| **1（男）** | FemaleCount > 0 | ❌ 拒绝 | 男女混住禁止 |
| **2（女）** | 总人数 = 0（空房）| ✅ 放行 | 任何人都可进空房 |
| **2（女）** | FemaleCount > 0, MaleCount = 0 | ✅ 同性别 OK | — |
| **2（女）** | MaleCount > 0 | ❌ 拒绝 | 男女混住禁止 |
| **0（未知）** | 总人数 = 0（空房）| ✅ 放行 | 任何人都可进空房 |
| **0（未知）** | 总人数 > 0 | ❌ 拒绝 | 未知员工禁止与已住人员混住 |

#### 实现代码（L1259-1284）

```csharp
// 规则 1：余量校验
var available = d.Capacity - totalCount - reserved;
if (available <= 0) continue;

// 规则 2：v2.13.84 性别约束
// - 空房间（totalCount=0）：可选（任何 Gender 员工都能进）
// - 员工 Gender=0（未知）：仅当房间为空时可选
// - 员工 Gender=1（男）：现有必须是男（femaleCount=0）
// - 员工 Gender=2（女）：现有必须是女（maleCount=0）
if (totalCount == 0) {
    /* 空房间 → 放行 */
} else if (empGender == 0) {
    continue;   // L1275
} else if (empGender == 1 && femaleCount > 0) {
    continue;   // L1279 男不入女房
} else if (empGender == 2 && maleCount > 0) {
    continue;   // L1283 女不入男房
}
```

#### 三层防御（v2.13.82 业务硬约束规范）

| 层 | 位置 | 职责 |
|----|------|------|
| **UI 层** | `CheckIn.cshtml` option 文本 | 通过 R5 显示余量让用户预判 |
| **Service 层（兜底）** | `BookingService.cs` L656-684 CheckInAsync | 即使绕过 UI 仍校验 |
| **API 层** | `BookingController` | 与 Service 层冗余但不重复 |

### 3.3 R3：4 级智能排序（v2.13.112）

#### 定义

通过 R2 三层过滤后的房号，按以下优先级排序（每级内部按字典序）：

| 优先级 | 规则 | 实现 |
|--------|------|------|
| **P1** | 同员工班组（`HasSameTeam == 1`）| 房间内已入住员工有与所选员工相同班组 |
| **P2** | 空房号（`CurrentCount == 0`）| 优先空房（即使不同班组也排前）|
| **P3** | 同主要考勤班次（`MainAttendanceTypeId == empAttId`）| 房间主要班次匹配员工 AttendanceTypeId |
| **P4** | 字典序（`DormCode ASC`）| 兜底稳定排序 |

#### 实现代码（L1338-1344）

```csharp
// v2.13.112 4 级智能排序：同员工班组 > 空房 > 同班次 > 字典序
var sortedResult = result
    .OrderByDescending(d => d.HasSameTeam)                  /* P1 同员工班组 */
    .ThenByDescending(d => d.CurrentCount == 0)             /* P2 空房号 */
    .ThenBy(d => d.MainAttendanceTypeId == empAttId ? 0 : 1) /* P3 同班次 */
    .ThenBy(d => d.DormCode)                                /* P4 字典序 */
    .ToList();
```

#### 排序示例

```
员工 JG003032（班组=一班，班次=早）：
  D-301: 班组 一班/二班（含员工班组）+ 男 + 早 → 同班组+同班次 → #1
  D-302: 班组 一班/三班 + 男 + 早 → 同班组+同班次 → #2
  D-303: 空房 + 男 + 默认 → 空房优先 → #3
  D-304: 班组 二班 + 男 + 早 → 同班次 → #4
  D-305: 班组 三班 + 男 + 中 → 无 → #5
  D-401: 空房 + 女（不匹配员工男）→ 不在结果集
  D-402: 住满 → 不在结果集
```

### 3.4 R4：班组列派生（v2.13.112，仅展示不参与筛选）

#### 定义

每个房号下拉项末尾追加 `| 班组 A/B/C`：

- 班组名 = 该宿舍当前在宿员工的 `SysEmployee.TeamId → Team.Name` 去重集合
- 按 `Team.SortOrder` 升序 + 去重
- **空房显示 `-`**（v2.13.112 与 v2.13.111 不同：列表用空白字符，下拉框用 `-`）
- **"同班组" Badge**：当选员工班组与房间内某班组同名时显示

#### 实现代码（L1211-1227）

```csharp
// v2.13.112 派生班组（与 v2.13.111 同 EmployeeTeamMap 模式：仅显示不参与筛选）
var teamMap = await _db.DormBookings
    .Where(b => dormCodesForTeam.Contains(b.DormCode) && b.Status == BookingStatus.Staying)
    .Join(_db.Employees.AsNoTracking(),
          b => b.EmployeeId, e => e.Id,
          (b, e) => new { b.DormCode, e.TeamId })
    .Join(_db.Teams.AsNoTracking(),
          x => x.TeamId, t => t.Id,
          (x, t) => new { x.DormCode, TeamId = t.Id, TeamName = t.Name, SortOrder = t.SortOrder })
    .GroupBy(x => x.DormCode)
    .Select(g => new {
        DormCode = g.Key,
        TeamNames = g.OrderBy(x => x.SortOrder).ThenBy(x => x.TeamId)
                     .Select(x => x.TeamName).Distinct().ToList()
    })
    .ToDictionaryAsync(x => x.DormCode, x => x.TeamNames);
```

| 场景 | 班组列渲染 |

| A102 住 1 人（一班）| `一班` |
| A103 空房 | `-` |
| A104 住 2 人 + 员工班组 = 一班 | `一班/二班` + `[同班组 Badge]` |

### 3.5 R5：床位号自动计算（v2.13.88）

#### 定义

每个房号下拉项显示 `床位 {occupied}/{total} · 下一个分配 {nextBedNo}号`。

#### 计算公式

```
allBedNos = Dorm.BedNumbers.Split(',').Select(int.Parse)       // 例: "1,2,3,4" → [1,2,3,4]
occupiedBedNos = (bookingBedNos ∪ empBedNos).Distinct()        // 双源去重（R7 兜底）
availableBedNos = allBedNos.Except(occupiedBedNos).OrderBy(n => n)
nextBedNo = availableBedNos.FirstOrDefault()                   // 最小可用
```

#### 实现代码（L1286-1313）

```csharp
// v2.13.88 计算床位号：解析 Dorm.BedNumbers → 排除已占用 → 取最小可用
var allBedNos = string.IsNullOrWhiteSpace(d.BedNumbers)
    ? new List<int>()
    : d.BedNumbers.Split(',', StringSplitOptions.RemoveEmptyEntries)
        .Select(s => int.TryParse(s.Trim(), out var n) ? (int?)n : null)
        .Where(n => n.HasValue).Select(n => n!.Value).ToList();

// 来源 1：DormBooking.BedNo (Status=2 在宿)（v2.13.24+）
// 来源 2：SysEmployee.BedNo (fallback 历史脏数据)
var occupiedBedNos = new List<int>();
// ... bookingBedNos / empBedNos 双源拉取 ...
occupiedBedNos = occupiedBedNos.Distinct().ToList();

var availableBedNos = allBedNos.Except(occupiedBedNos).OrderBy(n => n).ToList();

```

### 3.6 R6：入口 filter 双重匹配（v2.13.121）

#### 定义

员工选择输入框必须支持**工号 + 姓名**双重搜索。前端二次过滤必须按 `(realName.includes(kw) || employeeCode.includes(kw))` 双重匹配，**禁止仅按 realName 匹配**。

#### 实现代码

**CheckIn.cshtml L279-282**：

```javascript
empSearchResults = res.data.filter(e =>
    (e.realName && e.realName.includes(kw)) ||
    (e.employeeCode && e.employeeCode.includes(kw))
);
```

**CheckOut.cshtml L165-170**（额外 `e.dormCode` 约束，仅保留在宿员工）：

```javascript
empSearchResults = res.data.filter(e =>
    e.dormCode && (
        (e.realName && e.realName.includes(kw)) ||
        (e.employeeCode && e.employeeCode.includes(kw))
    )
);
```

#### 为什么 R6 是入口规则

R1-R5（R2-R5 v2.13.116 + R1 v2.13.113）均依赖 `selectEmp` 被调用 + `refreshDorms` 被调用，但 **R6 失败时 selectEmp/refreshDorms 永远不调用**，R1-R5 全部失效。R6 是顺序链最前端的一条规则。

| 场景 | R6 失败后果 |
|------|-----------|
| 用户输入 "JG000607" | 下拉列表空 |
| 用户输入 "刘院飘" | 下拉列表 1 条 OK（realName 命中） |
| emp-info-card | 永不渲染（R1 失效） |
| 房号列表 | 永远显示"请选择房间"（R2-R5 失效） |

### 3.7 R7：床位号双源 fallback（v2.13.24 + v2.13.77）

#### 定义

计算已占用床位号时，必须**双源拉取 + 去重**：

| 优先级 | 数据源 | 条件 |
|--------|--------|------|
| **高** | `DormBooking.BedNo` | `Status == 2`（在宿）AND `BedNo.HasValue` |
| **低（兜底）** | `SysEmployee.BedNo` | `DormCode == 该房` AND `BedNo.HasValue` |

#### 为什么需要 fallback

- **v2.13.24 引入**：`DormBooking` 表新增 `BedNo` 字段
- **v2.13.77 联动**：`CheckInAsync` 三件套同步（DormCode + BedNo + ResidenceStatusId）
- **历史脏数据**：生产 DB 中**部分历史 `DormBooking.BedNo` 为 NULL**（v2.13.24 之前的数据）
- **后果**：仅取 `DormBooking.BedNo` 会**漏算**这些历史记录的占用床位号，导致分配重复

#### 实现代码（L696-728）

```csharp
// v2.13.88 床位号 fallback：基于 Dorm.BedNumbers 真实床位号
// v2.13.77 联动物联：SysEmployee.BedNo 同步
var occupiedBedNos = new List<int>();

// 来源 1：DormBooking.BedNo（Status=2 在宿）
var bookingBedNos = await _db.DormBookings
    .Where(b => b.DormCode == dormCode && b.Status == BookingStatus.Staying && b.BedNo.HasValue)
    .Select(b => b.BedNo!.Value)
    .ToListAsync();
occupiedBedNos.AddRange(bookingBedNos);

// 来源 2：SysEmployee.BedNo（fallback 历史脏数据）
var empBedNos = await _db.Employees
    .Where(e => e.DormCode == dormCode && e.BedNo.HasValue)
    .Select(e => e.BedNo!.Value)
    .ToListAsync();
occupiedBedNos.AddRange(empBedNos);

occupiedBedNos = occupiedBedNos.Distinct().ToList();
```

#### 验证

| 场景 | 期望行为 |
|------|---------|
| `DormBooking.BedNo` + `SysEmployee.BedNo` 一致 | 去重后正确 |
| 仅 `DormBooking.BedNo = 2`（SysEmployee 为 NULL） | 取 2 |
| 仅 `SysEmployee.BedNo = 3`（历史脏数据） | 取 3（fallback 生效）|
| 两者都是 NULL | 取 0（空床位）|

## 八、永久教训（3 大类）

### 8.1 规则集中化教训

> **「12 版本迭代产生的规则必须有一份终极汇总文档」** — v2.13.78 → v2.13.122 共 12 个版本迭代，每次新增/修改规则都伴随一份独立交付报告，导致维护者必须读 6+ 份文档才能拼出完整规则链。**v2.13.123 终极汇总 + 旧版 DEPRECATED 标记**是治理这种"规则碎片化"的标准模式。

### 8.2 入口链与下游规则依赖教训

> **「R6 是 R1-R5 的入口规则，R6 失败时所有下游规则失效」** — v2.13.121 发现的 BUG：前端 `realName.includes(kw)` 单字段过滤导致按工号搜索时下拉列表为空，进而 `selectEmp` / `refreshDorms` 永远不调用，R1-R5 全部不可触达。**核心原则**：入口规则必须与下游规则**对称覆盖**（API WHERE 包含 N 个 LIKE 字段，前端 filter 必须包含 N 个 includes）。

### 8.3 字节级 1:1 对齐教训

> **「100% 1:1 对齐不只是 UI 看起来一样」** — v2.13.121 修复入口 BUG 后，v2.13.122 进一步发现 5 项差异（字段独立项 + 单字化 + bi-gender 图标 + alert-warning 类 + value 回写），每一项差异都是潜在 BUG 源头。**核心方法**：对原型 + 当前实现做**字节级 grep 对比**，包括字段顺序、字段层级、CSS 类、图标系统、value 回写、文案细节（单字 vs 多字）。

### 8.4 FK 单一真源教训

> **「冗余字符串字段永远不能信任」** — `SysEmployee.Department` / `SysEmployee.Team` 等冗余字符串字段在生产 DB 中可能为 NULL 或与 FK Name 不一致。**单一真源 = `xxxId FK → Table.Name`**，所有 UI 渲染必须走 FK 派生，禁止 fallback 字符串字段。v2.13.78 (班组 FK) + v2.13.113 (selectEmp FK) + v2.13.112 (排序 JOIN Team) 共 3 个版本逐步覆盖了 5 个渲染位置。
