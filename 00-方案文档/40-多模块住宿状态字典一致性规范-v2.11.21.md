## 1. 问题诊断

### 1.1 多套同名/近义"住宿/状态"定义并存

| # | 来源 | 定义 | 概念 | 数量 |
|---|------|------|------|------|
| 1 | **基础资料 ResidenceStatus** | LODGED=已住宿 / NOT_LODGED=未住宿 / PENDING=待入住 | 人员维度住宿状态 | 3 项 |
| 2 | **办理登记 DormBooking.Status** | 1=预约 / 2=在宿 / 3=已退房 / 4=已取消 | 单条 BOOKINGS 流水状态 | 4 项 |
| 3 | **员工账单 segmentType** | LIVING=在宿 / TRANSFER_OUT=调出段 / TRANSFER_IN=调入段 | 账单段类型（员工账单专用）| 3 项 |
| 4 | 人员清单 getLivingStatus (旧) | LIVING/LEFT/BOOKED/CANCELLED/NONE | ❌ 历史遗留，已废弃 | 5 项 |

### 1.2 用户视角的混乱

| 场景 | 用户预期 | 实际不一致 |
|------|---------|----------|
| 办理登记列表筛选"状态" | 应显示流水状态（4 项） | ✅ 已使用 BOOKING_STATUS_DICT |
| 员工账单列表"住宿状态"列 | 应与筛选下拉一致 | ❌ 列显示 segmentType，筛选显示 ResidenceStatus |
| 人员清单"住宿状态"列 | 应是人员维度状态 | ❌ 历史使用 5 项旧枚举（v2.11.20 已修订）|

### 1.3 根本原因

历史上"住宿状态"被用于多个不同概念：
- **人员维度住宿状态**（已在 v2.11.20 与基础资料 ResidenceStatus 统一）
- **办理登记流水状态**（业务字段 int 1-4，未抽象为字典）
- **账单段类型**（员工账单专用，未抽象为字典）

三套定义的数据规则与名称各异，导致用户在不同模块看到不一致的"住宿状态"。

## 2. v2.11.21 强制规范：三套独立字典

### 2.1 字典1：基础资料-住宿状态（ResidenceStatus）

> **数据源**：`ResidenceStatus` 表（DormManage.Shared/Models/ResidenceStatus.cs）

| ID | Code | Name | Badge | 业务含义 |
|----|------|------|-------|---------|
| 1 | LODGED | 已住宿 | bg-primary | 人员当前正在住宿（BOOKINGS.Status=2 在宿） |
| 2 | NOT_LODGED | 未住宿 | bg-light text-dark | 人员当前未住宿（退房后/已取消/无记录） |
| 3 | PENDING | 待入住 | bg-warning text-dark | 人员当前预约未入住（BOOKINGS.Status=1 预约） |

**使用范围**：
- 人员清单住宿状态列（派生）
- 员工账单列表筛选下拉
- 任何需要展示"人员维度整体住宿"的页面

**FK 关联**：`SysEmployee.ResidenceStatusId` → `ResidenceStatus.Id`

### 2.2 字典2：办理登记流水状态（BOOKING_STATUS_DICT，v2.11.21 新增）

> **数据源**：`BOOKING_STATUS_DICT`（mock-data.js 新增）；后端对应 `DormBooking.Status` 字段

| ID | Code | Name | Badge | 业务含义 |
|----|------|------|-------|---------|
| 1 | RESERVED | 预约 | bg-warning text-dark | 已预约未实际入住 |
| 2 | STAYING | 在宿 | bg-success | 入住登记生效中 |
| 3 | CHECKED_OUT | 已退房 | bg-secondary | 退房办理完成 |
| 4 | CANCELLED | 已取消 | bg-danger | 预约已取消 |

**使用范围**：
- 办理登记列表 Status 列
- 办理登记列表 Status 筛选下拉
- 任何需要展示"单条 BOOKINGS 记录生命周期"的页面

**数据存储**：`DormBooking.Status` INT 字段（无需新增 FK 字典表，BOOKINGS 是高频写入表）

### 2.3 字典3：账单段类型（EMPLOYEE_BILL_SEGMENT_TYPE，v2.11.21 新增）

> **数据源**：`EMPLOYEE_BILL_SEGMENT_TYPE`（mock-data.js 新增）；后端对应 `EmployeeBill.SegmentType` 字段

| ID | Code | Name | Badge | 业务含义 |
|----|------|------|-------|---------|
| 1 | LIVING | 在宿段 | bg-success | 完整在宿期间的分摊 |
| 2 | TRANSFER_OUT | 调出段 | bg-warning text-dark | 调出前在原住宿期间的分摊 |
| 3 | TRANSFER_IN | 调入段 | bg-info text-dark | 调入后在新住宿期间的分摊 |

**使用范围**：
- 员工账单列表"账单段类型"列（原"住宿状态"列已重命名）
- 任何需要展示"账单段类型"的页面

**数据存储**：`EmployeeBill.SegmentType` NVARCHAR(20) 字段（无需新增 FK 字典表）

## 3. 概念边界对照表

| 维度 | 字典 | 概念 | 应用场景 |
|------|------|------|---------|
| **人员维度住宿** | ResidenceStatus | 这个人目前是否在住宿？ | 人员清单、首页 KPI |
| **流水维度状态** | BOOKING_STATUS_DICT | 这条办理记录目前什么状态？ | 办理登记列表 |
| **账单段类型** | EMPLOYEE_BILL_SEGMENT_TYPE | 这条账单属于哪段时间？ | 员工账单列表 |

> **v2.11.21 强制规范**：
> - 三个字典**不可混用**
> - 任何一个页面/接口新增"住宿/状态"字段，必须先确定属于哪个维度，然后引用对应字典
> - 禁止跨字典引用（如禁止把 ResidenceStatus 用于 BOOKINGS 流水状态展示）

## 6. 长期约束

### 6.1 强制规范

1. **三套字典不可混用**：每个字典有明确的应用场景，禁止跨字典引用
2. **新增字典必须明确概念维度**：未来新增"住宿/状态"相关字典前，必须先明确属于"人员维度/流水维度/账单维度/其他维度"
3. **页面列名必须明确**：避免使用"住宿状态"这种歧义名称，应使用具体维度名（如"人员住宿状态"/"办理登记状态"/"账单段类型"）
4. **下拉筛选与列表列必须同源**：同一字段的筛选下拉和列表列必须引用同一字典

### 6.2 PR/CI 检查项

| 检查项 | 类型 |
|-------|------|
| mock-data.js 三套字典定义完整 | 自动化 |
| booking/index.html 使用 BOOKING_STATUS_DICT | 代码审查 |
| employee-bills.html 列名与字典引用一致 | 代码审查 |
| 禁止跨字典引用 | 代码审查 |
