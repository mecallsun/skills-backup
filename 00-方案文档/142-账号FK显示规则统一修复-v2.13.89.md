## 一、Context（背景）

### 1.1 用户原话

> "所有 页面中 涉及登录账号的 记录 显 在数据表中关联 账号的id FK主键，但页面中显示为 姓名，例如：入住信息录入 页面中 登记人 在页面中应显示为 关联账号id 的 姓名；请全面检查这个数据逻辑规则 相关的功能需求，进行更正相关逻辑，完善补充 原型 及程序生成，更新开发 相关文档"

### 1.2 业务硬约束

**所有"登录账号"相关字段必须遵循以下双轨制**：

| 层级 | 存储 | 渲染 |
|------|------|------|
| **物理真理源** | `int UserId`（FK → SysUser） | JOIN SysUser → `DisplayName` |
| **冗余备份** | `string Username`（NVARCHAR(64)） | 兜底显示（FK 缺失时回退） |

**核心原则**：
1. 表必须存 `UserId` FK（不依赖冗余字符串）
2. 页面渲染必须 `JOIN SysUser` 取 `DisplayName`
3. 写入时同时写 FK + 冗余（向后兼容）

### 3.2 SQL FK 约束（v2.13.89 不加）

**决策**：本次不添加 SQL FK 约束。

**原因**：
- EF Core 通过 Fluent API 将 `SysUser.Id` 映射到 `UserId` 列
- SQL FK 约束若直接引用 `SysUser(UserId)` 会与 EF Core 的 INSERT 流程冲突
- EF Core 在 INSERT 时先 INSERT 父表再 INSERT 子表，但 SqlClient 默认不发送列名（用列位置）
- v2.13.89 内部测试验证：加 FK 约束 → INSERT NULL FK=0 → 触发 FK 冲突
- **解决方案**：在 C# 层（Domain Service）维护 FK 一致性，DB 层不强制

```csharp
public static int GetCurrentUserId(this HttpContext ctx)
{
    // v2.13.89：优先从 X-User-Id Header 获取（API 调用方可能未走 Cookie 认证）
    var headerId = ctx.Request.Headers["X-User-Id"].FirstOrDefault();
    if (!string.IsNullOrEmpty(headerId) && int.TryParse(headerId, out var hid)) return hid;

    // 其次从 Claims 中获取
    var c = ctx.User?.FindFirst(ClaimTypes.NameIdentifier);
    return c != null && int.TryParse(c.Value, out var id) ? id : 0;
}
```

### 6.1 列表 GetListAsync — JOIN 3 张 SysUser 表

```csharp
var userJoin =
    from q in query
    join rUser in _db.SysUsers.AsNoTracking() on q.Booking.RegistrarUserId equals rUser.Id into rGroup
```

### 6.2 单条 EnrichWithDisplayNameAsync

```csharp
/// <summary>
/// v2.13.89：填充 DormBooking 的 DisplayName 派生字段（JOIN SysUser）
/// — 单条返回路径使用（列表路径已在 GetListAsync 内 JOIN）
/// — 性能：1 次 IN 查询拉取所有 FK → DisplayName，避免 N+1
/// </summary>
private async Task EnrichWithDisplayNameAsync(params DormBooking[] bookings)
{
    var ids = bookings
        .SelectMany(b => new int?[] { b.RegistrarUserId, b.CheckInOperatorUserId, b.CheckOutOperatorUserId })
        .Where(id => id.HasValue && id.Value > 0)
        .Select(id => id!.Value)
        .Distinct()
        .ToList();
    if (ids.Count == 0) return;

    var users = await _db.SysUsers.AsNoTracking()
        .Where(u => ids.Contains(u.Id))
        .ToDictionaryAsync(u => u.Id, u => u.DisplayName);

    foreach (var b in bookings)
    {
        if (b.RegistrarUserId.HasValue && users.TryGetValue(b.RegistrarUserId.Value, out var rName))
            b.RegistrarDisplayName = rName;
        else if (!string.IsNullOrEmpty(b.Registrar))
            b.RegistrarDisplayName = b.Registrar;
        // CheckIn / CheckOut 同理
    }
}
```

## 九、关键决策与权衡

| 决策 | 理由 |
|------|------|
| **FK + 字符串 双轨制** | 物理真源是 FK（保证一致性）；冗余字符串用于 FK 缺失时兜底（向后兼容历史脏数据） |
| **不添加 SQL FK 约束** | EF Core Fluent API 已维护 FK 关系；SQL FK 约束会与 EF INSERT 流程冲突 |
| **HttpContext 双 Header 支持** | 与现有 GetCurrentUserName（X-User-Name → Claims）模式对称 |
| **列表 1 次 SQL JOIN** | 3 张表 LEFT JOIN SysUser（rUser/ciUser/coUser），性能可控 |
| **单条 1 次 SQL IN** | EnrichWithDisplayNameAsync 用 `WHERE Id IN (...)` 避免 N+1 |
| **DisplayName [NotMapped]** | 派生字段不持久化，避免冗余更新问题 |
| **SysConfig 不联动** | 表是种子数据静态表，无业务写入路径；FK 字段已加预留扩展 |

## 十一、风险与回退

### 11.1 历史脏数据 NULL FK 风险

**风险**：v2.13.89 前写入的历史 DormBooking 记录 `RegistrarUserId=NULL`。

**缓解**：
- 前端 `RegistrarDisplayName` 计算回退到 `Registrar`（冗余字符串），不会显示空白
- 未来可执行 Repair API（`POST /api/v1/bookings/repair-employee-names` 扩展为同步 Operator）

### 11.2 SysConfig FK 暂时闲置

**风险**：`UpdatedByUserId` 字段加但无业务写入。

**缓解**：DB 层就绪，未来任何 SysConfig 写入入口（如 `/Settings` 配置开关）即可启用。

### 11.3 EF Core `Id` 隐式映射冲突

**风险**：`SysUser.Id` 实际映射到 `UserId` 列；EF Core 列位置 INSERT 可能触发 SQL FK 约束。

**缓解**：v2.13.89 不加 SQL FK 约束，仅 C# 层维护一致性。
