# 费用标准 时段重叠检查按员工类型筛选 修复（v2.13.63）

> **版本**：v2.13.63
> **日期**：2026-07-21
> **类型**：P0 BUG 修复（接续 v2.13.61/62）+ 业务规则更正
> **结论**：✅ **时段重叠检查限定为「同员工类型 + 已生效」记录；不同类型的标准可同时启用**

---

## 一、BUG 描述

**用户报告原文**：
> 在 "编辑费用标准" 中的 "启用此标准" 的勾选没有生效；仅对同员工类型 已生效 的 记录进行 时段重叠进行检；如果同类型且已生效且时间段重叠，则提示："该时段已存在启用中的费用标准" 相似提示，否则正常生效；请查明原因并修复

**两个层面的问题**：

| # | 问题 | 现状 |
|---|------|------|
| 1 | "启用此标准"勾选没有生效 | 用户启用某类型标准时被错误拒绝，显示「该时段已存在启用中的费用标准」错误 |
| 2 | 时段重叠检查未按员工类型筛选 | 旧实现对所有激活的标准做重叠检查，导致不同员工类型互斥 |

## 二、深度根因排查

### 2.1 现状数据库（修复前）

```sql
SELECT Id, StandardName, ApplicableTypeId, IsActive, EffectiveFrom, EffectiveTo FROM BillingStandard;
-- Id=1, TypeId=1(合同工), IsActive=False, [2026-01-01, ∞)
-- Id=2, TypeId=2(临时工), IsActive=True,  [2026-01-01, ∞)
-- Id=3, TypeId=1(合同工, 名称"外包人员"), IsActive=False, [2026-01-01, ∞)
```

只有 Id=2（临时工）启用。

### 2.2 用户场景

用户在 Id=3（合同工类型）编辑页面，**勾选启用**，提交保存。

→ 期望：保存成功（不同员工类型）
→ 实际：保存失败，页面显示「该时段已存在启用中的费用标准」

### 2.3 旧版 BillingService.SaveStandardAsync 校验逻辑（v2.13.62）

```csharp
if (standard.IsActive)
{
    var today = DateOnly.FromDateTime(DateTime.Today);
    var existingActive = await _db.BillingStandards
        .AnyAsync(s => s.Id != standard.Id && s.IsActive
            && s.EffectiveFrom <= today
            && (s.EffectiveTo == null || s.EffectiveTo >= today));
    if (existingActive)
        return (false, "该时段已存在启用中的费用标准");
}
```

**根因**：
1. ❌ **没有按 `ApplicableTypeId` 过滤** — 不同员工类型的标准被错误互斥
2. ❌ **基于「覆盖今天」的反向推断** — 假设新标准的有效时段「正在生效」，未做真正的时段重叠检查

### 2.4 业务规则确认（用户意图）

**正确规则**：
- ✅ 仅对**同员工类型（ApplicableTypeId 相等）+ 已生效（IsActive=True）+ 时段重叠**的记录做互斥检查
- ✅ 不同时段 / 不同类型 → 允许并存
- ✅ 时段重叠定义：两个范围 `[a1, a2]` 与 `[b1, b2]` 重叠当且仅当 `a1 <= b2 AND b1 <= a2`
- ✅ 任一端为 null（永久有效）视为无穷大，比较时跳过对应约束

## 三、修复方案（v2.13.63）

### 3.1 BillingService.SaveStandardAsync 校验改造

```csharp
if (standard.IsActive)
{
    var newStart = standard.EffectiveFrom;
    // v2.13.63 修复：仅对【同员工类型 + 已生效】的记录做时段重叠检查
    // 重叠定义：newStart <= existingEnd AND existingStart <= newEnd
    // 任一端为 null（永久有效）视为无穷大，比较时跳过对应约束
    var hasOverlap = await _db.BillingStandards
        .AnyAsync(s => s.Id != standard.Id
            && s.IsActive
            && s.ApplicableTypeId == standard.ApplicableTypeId
            && (standard.EffectiveTo == null || s.EffectiveFrom <= standard.EffectiveTo)
            && (s.EffectiveTo == null || newStart <= s.EffectiveTo));
    if (hasOverlap)
        return (false, "该员工类型在此时段已存在启用中的费用标准");
}
```

### 3.2 修复要点

| 维度 | v2.13.62 旧逻辑 | v2.13.63 新逻辑 |
|------|----------------|----------------|
| 类型筛选 | ❌ 无（所有标准） | ✅ `s.ApplicableTypeId == standard.ApplicableTypeId` |
| 重叠检查 | ⚠️ 反向推断「覆盖今天」 | ✅ 真正的双时段重叠（双端 + null 容错） |
| 错误消息 | "该时段已存在启用中的费用标准" | "该员工类型在此时段已存在启用中的费用标准"（更精准） |
| null end | 视为「永久有效」 | 视为「永久有效」（向后兼容） |

## 七、教训总结（v2.13.61 → v2.13.63）

### 7.1 三个核心教训

1. ❌ **业务规则校验必须按业务主键（员工类型）分组** — 校验时缺少主键过滤会导致不同维度的数据被错误互斥
2. ❌ **「反向推断」校验不可靠** — 不要基于「覆盖今天」推断时段重叠，应该做真正的双时段重叠检查
3. ❌ **错误消息不精确会误导用户** — 「该时段已存在」让用户以为 checkbox 没保存，实际是业务规则拒绝

### 7.2 强制检查清单（业务规则校验）

- [ ] 互斥检查必须按业务主键（员工类型、部门、楼栋等）分组
- [ ] 时段重叠做真正双向检查：`a1 <= b2 AND b1 <= a2`
- [ ] null 端视为「永久有效」，比较时跳过对应约束
- [ ] 错误消息要精确指明冲突原因（哪个字段冲突）
- [ ] curl POST 验证：跨类型、跨时段、同类型冲突 3 个场景都要覆盖
