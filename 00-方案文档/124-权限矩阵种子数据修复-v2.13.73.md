### 2.2 根因解释

EF Core 的 `modelBuilder.Entity<T>().HasData(...)` 是 **声明式模型配置**：
- 仅在以下时机把 seed 数据 INSERT 到数据库：
  1. `Database.EnsureCreated()`（首次创建 schema 时）
  2. `dotnet ef database update`（执行 migrations 时）
- 对于**已有手动 DDL 的生产数据库**，seed 数据**不会自动应用**

本项目生产 SQL Server 数据库是 v2.13.22 起手动部署的（`01_DDL_Schema.sql`），从未执行过 `EnsureCreated()` 或 migrations，因此 `SysPermission` + `SysRolePermission` 始终为空。

## 六、教训

### 6.1 关键教训

1. **EF Core `HasData()` 是声明式，不自动 INSERT**：
   - 只在 `EnsureCreated()` 或 migrations 时插入
   - 生产数据库手动 DDL 后必须**手动**或通过 `DatabaseInitializer` 同步 seed
   - **审计脚本**：`SELECT COUNT(*) FROM SysPermission` 应在每次生产部署后验证

2. **PowerShell `Get-Content -Raw` 编码陷阱**：
   - 当 SQL 文件含中文（`N'首页看板'`）或特殊字符时，`Get-Content -Raw` 可能误判编码
   - **必须用 `[System.IO.File]::ReadAllText()`** 显式读取

3. **`SET IDENTITY_INSERT ON` 是必需的**：
   - `SysPermission.Id` 是 IDENTITY 列
   - 显式 INSERT 时必须先 `SET IDENTITY_INSERT SysPermission ON`，完成后 `OFF`

4. **审计时不能只看代码层**：
   - 模板正确 + 代码正确 + HasData 声明正确，**都不能保证 DB 有数据**
   - 必须在数据库层面验证（SELECT COUNT(*)）才能定位问题

### 6.2 防御性修复

- 建议添加 **`DatabaseInitializer.InitializeAsync`** 中 SysPermission / SysRolePermission 的 seed 检查：
  - 启动时 `SELECT COUNT(*) FROM SysPermission`
  - 如果为 0 → 打印 WARN 日志并自动 INSERT（用 DbContext HasData 同款数据）
- 这样未来任何部署都能自动恢复缺失的 seed

### 6.3 同步状态

- **DormDbContext.cs seed 声明**：保持不变（仍是 18 + 29 条）
- **生产 SQL Server**：已补齐 18 + 29 条
- **`DatabaseInitializer`**：暂未自动 seed（防御性优化待后续版本）

## 八、与 CLAUDE.md 全局规则的关系

本案例触发 CLAUDE.md 中 P0 架构约束的扩展：

> **任何修改 EF Core DbContext seed 后必须同步生产数据库**：`HasData()` 仅在 EnsureCreated / migrations 时执行；手动 DDL 部署的项目必须在 `DatabaseInitializer.InitializeAsync` 中添加 seed 同步逻辑（`SELECT COUNT(*) == 0 → INSERT`），否则生产库会一直缺少 seed 数据。
