# 129 — 人员清单班组 FK 关联修复（v2.13.78）

> **结论**：✅ **v2.13.78 修复人员清单列表班组列显示异常 BUG**：列表项「班组」列永远显示 "-" 或空字符串，根因是 EF Core 模型层「过度声明」了 `SysEmployee.Team` 字符串字段但实际 DB 中不存在该列；本次通过添加 `Team` 导航属性 + 移除 `Ignore` + Personnel Index `Include` + DTO 用 FK 名称等 4 层修复彻底解决。

## 一、用户反馈（2026-07-21）

> *"人员清单列表中没有正常显示班级信息，查明原因，应该是存储班级分类列表中的 id FK 关联，列表中显示对应的名称，请修复 BUG，更正相关的规则逻辑文档"*

注：用户口中「班级」实际为业务模型「班组」（`Team` 表）。

## 二、BUG 根因审计（5 层问题叠加）

### 2.1 数据真相源（DB Schema）

```sql
-- 真实生产 SQL Server 表结构（v2.13.6 修复后）
SELECT TOP 10 EmployeeId, RealName, TeamId
FROM SysEmployee
ORDER BY EmployeeId
```

**结论**：SysEmployee 表**只有 `TeamId`（FK INT NOT NULL）** 列，**没有 `Team` 字符串列**。
（验证：`SELECT Team FROM SysEmployee` → "列名 'Team' 无效" 异常）

### 2.2 EF Core 模型层（过度声明）

**`DormManage.Shared/Models/SysEmployee.cs`** 同时声明了：

```csharp
/// <summary>班组ID（对应真实表 TeamId，NOT NULL）</summary>
public int TeamId { get; set; }      // ✅ DB 列存在

/// <summary>班组（v2.13.3 补充字段，对应基础资料-班组表 Team 字符串）</summary>
[MaxLength(20)]
public string? Team { get; set; }    // ❌ DB 列不存在（孤儿属性）
```

**根因 #1**：声明了 `Team` 字符串字段但 DB 实际无此列 → 引入 v2.13.3 时未同步移除。

### 2.3 EF Core 映射层（显式 Ignore）

**`DormManage.Shared/Data/DormDbContext.cs` line 273**（v2.13.6 修复时加入）：

```csharp
entity.Ignore(e => e.Team); // 真实表无 Team 字符串列（仅 TeamId FK），
                            // 班组显示/筛选需改 TeamId 关联，属后续增强
```

**根因 #2**：v2.13.6 通过 `Ignore(e.Team)` 屏蔽了不一致，但**未跟进修复查询层 + 视图层**，导致 DTO 赋值仍读 `e.Team`（永远返回 null）。

### 2.4 查询层（缺 Include）

**`DormManage.Admin/Pages/Personnel/Index.cshtml.cs` line 160-163**：

```csharp
var query = _db.Employees
    .Include(e => e.EmployeeType)      // ✅ 员工类型导航属性
    .Include(e => e.AttendanceType)    // ✅ 考勤班次导航属性
    // ❌ 缺 .Include(e => e.Team) 班组导航
    .AsQueryable();
```

**根因 #3**：查询没 `Include Team`，且 SysEmployee 根本没 Team 导航属性。

### 2.5 视图层（DTO 读冗余字段）

**`DormManage.Admin/Pages/Personnel/Index.cshtml.cs` line 223**：

```csharp
TeamName = e.Team ?? "-",    // ← 读字符串孤儿属性（永远 null → 显示 "-"）
```

**根因 #4**：DTO 试图读 `e.Team` 字符串，孤儿属性永远 null，列表全部显示 "-"。

### 2.6 Edit / Create / Import 路径 6 处连带错误

| 文件 | 行 | 旧代码（BUG） | 修复 |

| `PersonnelService.ExportCsvAsync` | 119 | 同上 | 同上 |

## 三、修复方案

### 3.1 添加 Team 导航属性

**`DormManage.Shared/Models/SysEmployee.cs`** 新增：

```csharp
/// <summary>班组ID（对应真实表 TeamId，NOT NULL）</summary>
public int TeamId { get; set; }

/// <summary>
/// 班组导航属性（v2.13.78 新增，对应基础资料-班组表 Team）
/// </summary>
[ForeignKey(nameof(TeamId))]
public Team? Team { get; set; }
```

### 3.2 移除 `Ignore` + 配置 FK 关系

**`DormManage.Shared/Data/DormDbContext.cs`**：

```csharp
// 删除 v2.13.6 加入的 Ignore 行：
- entity.Ignore(e => e.Team);

// 在 ResidenceStatus 关系后面新增：
+ // v2.13.78 BUG 修复：班组 FK 关联引用基础资料-班组表 Team
+ entity.HasOne(e => e.Team)
+       .WithMany()
+       .HasForeignKey(e => e.TeamId)
+       .OnDelete(DeleteBehavior.Restrict);
```

### 3.3 Personnel Index 加 Include + DTO 用 FK 名称

**`DormManage.Admin/Pages/Personnel/Index.cshtml.cs`**：

```csharp
var query = _db.Employees
    .Include(e => e.EmployeeType)
    .Include(e => e.AttendanceType)
    .Include(e => e.Team)              // ← v2.13.78 新增
    .AsQueryable();

// ... 投影 ...
TeamId = e.TeamId,
TeamName = e.Team != null ? e.Team.Name : "-",  // ← 走 FK 关联
```

### 3.4 Service 层班组筛选条件走 FK

**`DormManage.Shared/Services/PersonnelService.cs`**：

```csharp
// 之前（BUG）：直接比对字符串字段
- if (!string.IsNullOrWhiteSpace(team))
-     query = query.Where(e => e.Team == team);

// 之后（v2.13.78）：字符串班组名 → TeamId FK 关联
+ if (!string.IsNullOrWhiteSpace(team))
+ {
+     var teamId = await _db.Teams
+         .Where(t => t.Name == team || t.Code == team)
+         .Select(t => (int?)t.Id)
+         .FirstOrDefaultAsync();
+     if (teamId.HasValue)
+         query = query.Where(e => e.TeamId == teamId.Value);
+     else
+         query = query.Where(e => false); // 班组名称无匹配 → 空结果
+ }
```

### 3.5 移除孤儿属性赋值

所有 `Team = teamName,` 字面赋值的代码位置（6 处）已改为「仅写 `TeamId`」。

## 四、规则逻辑文档更新

### 4.1 业务规则更新

**单一数据源原则**：班组信息**只通过 `TeamId` FK 字段 + 班组表（Team）Name 显示**，禁止在 SysEmployee 表上保留任何冗余字符串字段。

**白名单 FK 关联引用域**（v2.13.78 起，所有列表/详情/筛选/导入/导出统一规则）：

| 显示列 | FK 字段 | 关联基础资料表 | 显示来源 |
|--------|---------|---------------|---------|
| 员工类型 | `EmployeeTypeId` | `EmployeeType` | `.Name` |
| 考勤班次 | `AttendanceTypeId` | `AttendanceType` | `.Name` + `.Code` |
| 在职状态 | `EmploymentStatusId` | `EmploymentStatus` | `.Name` |
| 住宿状态 | `ResidenceStatusId` | `ResidenceStatus` | `.Name` |
| **班组** | **`TeamId`** | **`Team`** | **`.Name`**（v2.13.78 起） |
| 部门 | `Department`（字符串） | - | 直接字段（v2.13.24 起也是冗余，待后续升级） |

### 4.2 关联查询模式（v2.13.78 标准模板）

```csharp
var query = _db.SysEmployees
    .Include(e => e.EmployeeType)
    .Include(e => e.AttendanceType)
    .Include(e => e.EmploymentStatus)
    .Include(e => e.ResidenceStatus)
    .Include(e => e.Team)               // ← v2.13.78 起强制
    .AsQueryable();

// DTO 投影：
EmployeeTypeName = e.EmployeeType?.Name ?? "-",
AttendanceTypeName = e.AttendanceType?.Name ?? "-",
EmploymentStatusName = e.EmploymentStatus?.Name ?? GetStatusName(e.EmploymentStatusId),
ResidenceStatusName = e.ResidenceStatus?.Name ?? "-",
TeamName = e.Team?.Name ?? "-",         // ← v2.13.78 起
```

### 4.3 Import / Export 规则

- **导入**：Excel 列「班组」接受「班组名称 / 班组 Code」两种值；内部转 `TeamId` 后持久化
- **导出**：CSV 列「班组」输出 `Team.Name`（FK JOIN 取最新名称，避免冗余字段不一致）

## 六、关键决策与权衡

| 决策 | 理由 |
|------|------|
| **彻底移除 SysEmployee.Team 孤儿属性** | DB 无此列；孤儿属性是 BUG 温床（任何引用都会编译通过但运行 null）|
| **添加 Team 导航属性而非 string FK 嵌入查询** | 与 EmployeeType/AttendanceType/EmploymentStatus/ResidenceStatus 一致；统一模式 |
| **PersonnelService.GetListAsync 字符串班组名 → TeamId 解析** | 保留外部接口名 `string? team`，向后兼容调用方（API Controller / Import）|
| **不写 `Migration` 迁移（数据库无变更）** | DB 物理结构无变更；只是 EF Core 模型层修正；零数据库维护成本 |

## 九、核心教训

1. **「模型层过度声明」是 EF Core 隐性 BUG 重灾区**：声明了 DB 中不存在的孤儿属性 → 编译过、运行 null、隐藏显示问题。永远以 DB 物理 schema 为真理源
2. **`entity.Ignore()` 是临时补丁**：v2.13.6 用 Ignore 屏蔽问题但未跟进查询层 / 视图层；只解决编译错误，未解决数据展示错误。修复原则 =「一次性彻底解决」
3. **单字段多源容易踩坑**：SysEmployee.Team 字段从 v2.13.3 的字符串过渡到 v2.13.6 的 Ignore，再到 v2.13.78 的导航属性 —— **3 个版本未彻底走通 FK 关联**，单字段跨越 13 个版本的演变。**根本原因**：未把「单一数据源」作为字段设计的首要原则
4. **「属后续增强」注释是定时炸弹**：v2.13.6 注释埋下「班组显示/筛选需改 TeamId 关联，**属后续增强**」—— 这个 TODO 跨越 13 个版本才解决。修复原则：**遇到 TODO 即刻修，否则累积成技术债**
5. **关联查询模式必须统一**：EmployeeType/AttendanceType/EmploymentStatus/ResidenceStatus 都有 `Include + .Name` 模式；唯独 Team 缺位。**正确做法**：建立「FK 关联字段白名单」并强制走相同模式
