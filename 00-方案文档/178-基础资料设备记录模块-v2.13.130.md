## 二、三层数据模型设计

v2.13.130 是「设备数据」三层递进抽象的关键中间层：

| 层 | 模块版本 | 表名 | 数据特征 | 关系 |
|----|---------|------|---------|------|
| **配置层** | v2.13.120 | DormMeter | 静态：房号 ↔ 表 ID 1:1 | UNIQUE 索引 + FK CASCADE |
| **日志层（本次）** | **v2.13.130** | **EquipmentReading** | **动态：某时间点一次读数流水** | **不 FK 到 DormMeter（PDA 直传可绕过）** |
| **聚合层** | v2.13.96 | MeterRecord | 月度聚合统计 | FK → DormId（CASCADE）|

### 为什么 EquipmentReading 不 FK 到 DormMeter？

- PDA 端离线模式抄表：可能 DormMeter 还未配置
- PDA 自动入库：直接走 EquipmentReading 日志层
- 手工补录：操作员直接录入日志，无需先建 DormMeter

**因此日志表是独立存储，设备 ID + 设备类型作为字段值（不强制外键），业务层按需 JOIN DormMeter 做「日志↔配置」对账**。

## 三、新增表 EquipmentReading

### 3.1 DDL

```sql
CREATE TABLE dbo.EquipmentReading (
    ReadingId       INT            IDENTITY(1,1) NOT NULL,
    EquipmentId     NVARCHAR(64)   NOT NULL,             -- 设备 ID（电表/冷水/热水表编号）
    EquipmentType   TINYINT        NOT NULL,             -- 1=电表 2=冷水 3=热水
    Reading         DECIMAL(12,2)  NOT NULL DEFAULT 0,
    ReadTime        DATETIME       NOT NULL,             -- 读取时间（业务读取时刻）
    Remark          NVARCHAR(500)  NULL,
    CreatedBy       NVARCHAR(64)   NULL,                 -- 记录创建人（审计）
    CreatedAt       DATETIME       NOT NULL DEFAULT GETDATE(),
    UpdatedAt       DATETIME       NULL DEFAULT GETDATE(),
    CONSTRAINT PK_EquipmentReading PRIMARY KEY CLUSTERED (ReadingId),
    CONSTRAINT CK_EquipmentReading_Type CHECK (EquipmentType BETWEEN 1 AND 3)
);
CREATE NONCLUSTERED INDEX IX_EquipmentReading_EquipmentId ON dbo.EquipmentReading (EquipmentId);
CREATE NONCLUSTERED INDEX IX_EquipmentReading_ReadTime    ON dbo.EquipmentReading (ReadTime);
CREATE NONCLUSTERED INDEX IX_EquipmentReading_Type_Time   ON dbo.EquipmentReading (EquipmentType, ReadTime);
```

### 3.2 索引策略

| 索引 | 用途 | 命中 SQL |
|------|------|----------|
| IX_EquipmentReading_EquipmentId | 查某设备最新读数 | `WHERE EquipmentId = ? ORDER BY ReadTime DESC` |
| IX_EquipmentReading_ReadTime | 按时间段查询/批量删除 | `WHERE ReadTime BETWEEN ? AND ?` |
| IX_EquipmentReading_Type_Time | 按类型 + 时间段聚合 | `WHERE EquipmentType = ? AND ReadTime BETWEEN ? AND ?` |

### 8.1 批量删除 Service 实现（ExecuteDeleteAsync 高性能）

```csharp
public async Task<ApiResponse<int>> DeleteEquipmentReadingsByTimeRangeAsync(DateTime startTime, DateTime endTime)
{
    if (startTime > endTime)
        return ApiResponse<int>.Fail("TIME_RANGE_INVALID", "起始时间必须早于或等于结束时间");

    var affected = await _db.EquipmentReadings
        .Where(x => x.ReadTime >= startTime && x.ReadTime <= endTime)
        .ExecuteDeleteAsync();  // 直发 SQL DELETE，EF Core 7+ 性能最佳

    return ApiResponse<int>.Ok(affected, $"批量删除成功，共删除 {affected} 条记录");
}
```

## 十、永久教训

### 10.1 「三层数据模型」抽象原则

| 层 | 用途 | 是否 FK 到上层 |
|----|------|--------------|
| 配置层 | 静态映射（房号 ↔ 表 ID）| — |
| 日志层 | 动态流水（设备读数事件）| ❌ 不 FK（允许绕过配置直接录入）|
| 聚合层 | 周期汇总（月度统计）| ✅ FK（强约束保证业务完整性）|

**教训**：日志层「不 FK 到 DormMeter」是经过 13 次 BUG 修复后才悟出的核心设计原则 —— **配置层和数据流解耦，PDA 原始上传可以绕过 DormMeter 直接落日志**。

### 10.2 v2.13.114 幂等模式的胜利

v2.13.108 IDENTITY_INSERT 修复 + v2.13.114 去掉硬编码 Id 模式 → v2.13.130 仅靠此模式就能在生产 DB 中安全 seed 5 个新权限码，**无需担心 Id 已被占用**。

### 10.3 弹窗独占模式（v2.13.81 + v2.13.130 复用）

批量删除 Modal 复用 v2.13.81 模式：`data-bs-backdrop="static" data-bs-keyboard="false"` + 二次确认 checkbox + 启用按钮逻辑。**「危险操作」场景必须配此模式**，避免误触丢失。

### 10.4 ExecuteDeleteAsync 性能模式

批量删除时 `ExecuteDeleteAsync`（EF Core 7+）直发 SQL DELETE，**避免 N+1 SELECT + Remove + SaveChangesAsync** 的开销。在 v2.13.65 删除用户 BUG 时也用此模式修复 DbUpdateConcurrencyException。

## v2.13.131 增量（2026-07-23）— 加载失败 BUG 终极修复

### 用户反馈

> "设备记录列表 中 查询 时，显示 加载失败，请刷新重试,WHY ?"

### 根因（深挖到 Windows Event Log）

v2.13.130 的 `DatabaseInitializer.MigrateFieldPermissionAsync` 里 5 个 equipment-reading 权限码 SQL 使用了硬编码 `Id=46-50` + `WHERE Id = N` 判定 + `SET IDENTITY_INSERT ON`。但此前手动 SQL 已用 IDENTITY 自动分配的 Id（103-107）seed 过同名 PermissionCode，导致：

1. `WHERE Id = 46` 返回 0（不存在）
2. 执行 `INSERT VALUES (46, N'equipment-reading:view', ...)`
3. **触发 `UQ_SysPermission_Code` UNIQUE 约束冲突**（SysPermission.Code 已存在 Id=103）
4. SqlException 被 try/catch 静默吞掉（仅 WARNING 日志）
5. 启动照常成功，但因为迁移方法签名包含此步骤且共用事务边界，间接导致 DBContext 状态被污染

**等等——这其实不是设备记录 API 加载失败的根因（API 单独测试返回 200 + 11 条）**。真正的 BUG 是 `loadEquipmentReadings()` JS 函数调用了**不存在**的 `updatePagination(...)` 函数 → ReferenceError → catch 块兜底"加载失败，请刷新重试"文案。

### 修复

#### 后端 (v2.13.131 P0 SQL 重构)

`DatabaseInitializer.cs` 13 行 SQL 重写 — **去掉所有 IDENTITY_INSERT + 硬编码 Id**，改用 v2.13.114 幂等模式：

```sql
-- v2.13.131 修复：按 PermissionCode 唯一性判断，不指定 Id（IDENTITY 自动）
```

### v2.13.132 永久教训

1. **AJAX 列表禁止使用服务端 `_PaginationPartial`**：服务端翻页用 `<a href>` 跳转会被 AJAX 容器吃掉，表现为「点翻页按钮整页刷新」。客户端分页器必须用 JS 事件绑定。

### 永久教训

1. **Dashboard 与业务页面数据口径必须严格一致**：本次发现 `DashboardService.cs` 原 `Status != Voided` 与 `Meter/Index.cshtml` 的 `Status IN (1, 2)` 不一致——首页 KPI 显示「已抄」但实际上把 `Status=0` 占位记录也算入，导致覆盖率高估。DashboardService 是派生计算源头，必须与源页面规则**字节级对齐**。
2. **`未完成 ≠ 未覆盖` 的语义区分**：v2.13.133 之前 DashboardService 用 `Status != Voided` 算「已抄」，再 `总 - 已抄 = 未抄`——把「未完成」和「未覆盖」合并为「未抄」一个数字。用户原话明确要 3 段拆分，**业务上必须区分**：已建立占位记录但数据不全（未完成）vs Dorm 表存在但完全无记录（未覆盖）——这两类操作含义完全不同。
3. **派生属性用 `=>` 计算表达式**：`MeterCoveragePercent` 是计算属性，不占 JSON 序列化成本，自动跟随 MeterReadCount / MeterTotalCount 同步。
