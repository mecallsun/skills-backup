## 一、BUG-003 修复（已完成）✅

### 用户报告
> 「设备记录的批量删除按钮功能出现信息为：错误：批量删除成功，共删除 0 条记录，但实际数据表中的数据没有任何变化」

### 根因诊断（端到端实测）
| 测试 | 字段格式 | 实际删除条数 | 原因 |
|------|---------|------------|------|
| **Test 1**（camelCase `startTime/endTime`）| 与 Admin 客户端一致 | **736 条** ✅ | 反序列化 + 范围匹配正常 |
| **Test 2**（PascalCase `StartTime/EndTime`）| 测试用 | **0 条** ❌ | 反序列化为 `default(DateTime)` → 范围 `0001-01-01` → 无匹配 |

### 真正的根因
`DormManage.Api/Program.cs` 和 `DormManage.Admin/Program.cs` 的 `AddJsonOptions` **只配了** `PropertyNamingPolicy = CamelCase`（**输出**侧），**没配** `PropertyNameCaseInsensitive = true`（**输入**侧）。

**ASP.NET Core 8 默认 `PropertyNameCaseInsensitive = false`**：
- 客户端发 camelCase → `PropertyNamingPolicy = CamelCase` → 映射到 C# `StartTime` PascalCase → **匹配成功** ✅
- 客户端发 PascalCase（不常用）→ 不通过 naming policy 转换 → **找不到匹配属性** → 字段被丢弃为 `default(T)` → 时间范围 `0001-01-01` → **0 条删除** ❌

### 用户报告的「0 条」最可能原因
- 用户选错时间范围（如选 2026-08-15 ~ 2026-09-30 而数据库 ReadTime 范围 2026-07-30~07-31）
- 或使用旧版 SDK / 第三方工具发 PascalCase 请求字段

### 修复（v2.13.173）

**`DormManage.Api/Program.cs`**：
```csharp
builder.Services.AddControllers()
    .AddJsonOptions(options =>
    {
        options.JsonSerializerOptions.PropertyNamingPolicy = System.Text.Json.JsonNamingPolicy.CamelCase;
        // v2.13.173 修复 BUG-003：增加 PropertyNameCaseInsensitive = true
        options.JsonSerializerOptions.PropertyNameCaseInsensitive = true;
        options.JsonSerializerOptions.DictionaryKeyPolicy = System.Text.Json.JsonNamingPolicy.CamelCase;
    });
```

**`DormManage.Admin/Program.cs`** 同步修复。

**编译**：0 error。

### 验证方式
- **源码级**：camelCase/PascalCase 双格式都应正常反序列化
- **端到端**（需要完整 TrayApp+Api+Admin 部署）：Admin 选时间范围后 → POST batch-delete → 应返回 `success: true, data: N`（N > 0）

## 四、永久教训

1. **ASP.NET Core 8 AddJsonOptions 默认不区分大小写**（`PropertyNameCaseInsensitive = false`）—— 配置 camelCase naming policy 时**必须同时**配 `PropertyNameCaseInsensitive = true`，否则 PascalCase 请求会全部丢失。
2. **批量删除类端点必测试「空范围」和「正常范围」两端**——空范围 0 条 vs 正常 N 条差距能快速发现反序列化 BUG。
3. **TimeSpan / DateTime 减法结果负值**永远说明「类型不匹配」或「减法方向错」—— 立即检查 `DateTimeKind`（Local vs Utc vs Unspecified）。
4. **BUG 报错中「包含中文错误信息」时，源码全文搜索** 是最快定位方法——若**零匹配**则说明错误来自代码库外部（其他端/历史版本/未提交本地修改）。
