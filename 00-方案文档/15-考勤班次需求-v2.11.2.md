## 1. 业务背景

### 1.1 问题

员工因倒班（早班/中班/晚班/夜班）作息时间差异大，混居同一宿舍时**相互影响休息**：
- 早班员工 22:00 入睡，夜班员工 02:00 归寝（产生噪音）
- 晚班员工中午休息，夜班员工上午补觉（开灯/洗漱）

### 1.2 目标

为每位员工标记**考勤班次**，宿舍分配时**尽量**（非强制）安排相同考勤班次的员工同住，降低互相干扰。

### 1.3 关键约束

- **非强制**：床位紧张时仍允许混合分配（避免空床）
- **优先级低于**：性别（预留扩展）、部门、员工类型
- **默认值**："默认"（早九晚五标准作息）

## 3. 宿舍分配智能规则

### 3.1 优先级（高 → 低）

1. **空床位 > 同类型 > 跨类型**（避免空床）
2. **同考勤班次**（核心目标）
3. **同部门**（辅助，便于沟通）
4. **同员工类型**（辅助，合同工/外包习惯相近）

### 3.2 分配算法（伪代码）

```python
def assign_dorm(person, available_dorms):
    # 1. 优先找：同考勤班次 + 同部门 + 有空位
    candidates = [d for d in available_dorms
                  if has_bed(d) and
                     d.attendance_type == person.attendance_type and
                     d.department == person.department]
    if candidates: return random(candidates)

    # 2. 次选：同考勤班次 + 同部门类型 + 有空位
    candidates = [d for d in available_dorms
                  if has_bed(d) and
                     d.attendance_type == person.attendance_type]
    if candidates: return random(candidates)

    # 3. 三选：任意有空位的宿舍（兜底）
    candidates = [d for d in available_dorms if has_bed(d)]
    if candidates: return random(candidates)

    # 4. 兜底：无空床位时记录异常（不分配）
    return None
```

### 3.3 实际效果（演示数据）

| 宿舍 | 容量 | 在住 | 考勤班次构成 |
|------|------|------|------------|
| D-001 | 4 人 | 4 人 | 4 早班 |
| D-002 | 4 人 | 4 人 | 3 夜班 + 1 默认 |
| D-003 | 4 人 | 3 人 | 3 晚班 |
| D-004 | 4 人 | 4 人 | 4 中班 |

> **典型场景**：早班宿舍 4 人都是 5:00 起床，夜班宿舍 4 人都是 7:00 起床，互不干扰。

### 4.4 后端 SQL（v2.11.7.BUGFIX 修正）

```sql
-- v2.11.7 修正：列表查询（JOIN Personnel + AttendanceType 表）
SELECT
    b.Id, b.EmployeeCode, b.EmployeeName,
    p.AttendanceTypeId,          -- FK（v2.11.7 修正：从 string 改为 int FK）
    at.Code AS AttendanceTypeCode,
    at.Name AS AttendanceTypeName, -- 通过 JOIN 取 Name 显示
    p.DepartmentId, d.Name AS DepartmentName,
    b.DormCode, b.Type, b.Status, b.BookingDate
FROM Booking b
LEFT JOIN SysEmployee p ON b.EmployeeId = p.Id
LEFT JOIN AttendanceType at ON p.AttendanceTypeId = at.Id
LEFT JOIN Department d ON p.DepartmentId = d.Id
WHERE b.Status IN (1, 2, 3)
ORDER BY b.BookingDate DESC;
```

> **v2.11.7 性能优化**：原 SQL 无需 JOIN `AttendanceType` 表即可显示（字段已在 Personnel 中），但 v2.11.7 修正后必须 JOIN。性能影响：通过 `Personnel(AttendanceTypeId)` 索引 + `AttendanceType.Id` 主键 索引即可，无需额外优化。

## 9. v2.11.7.BUGFIX 关联关系错误更正（强制）

> **⚠️ 重要历史修正**：本节记录 v2.11.7 修复的关联关系错误，避免后续重复犯错。

### 9.1 错误问题汇总

`15-考勤班次需求-v2.11.2.md` 原稿（v2.11.2 发布于 2026-07-11）存在多处与项目统一架构不一致的关联关系错误：

| # | 错误位置 | 原稿（错误） | 正确（v2.11.7 修正） | 错误原因 |
|---|---------|---------|----------|---------|
| 1 | §2.2 数据库字段 | `AttendanceType NVARCHAR(16)` | `AttendanceTypeId INT`（FK） | 违反 §9.1 "存储 ID 显示 Name" 强制规则 |
| 2 | §2.3 枚举定义 | `enum AttendanceType { DEFAULT, MORNING, ... }`（存枚举字符串） | 基础资料表 `AttendanceType`（FK 关联） | 与其他基础资料（部门/员工类型）架构不一致 |
| 3 | §4.4 SQL 查询 | `SELECT p.AttendanceType`（PERSONNEL 内字段） | `JOIN AttendanceType`（外键关联） | 1 + 2 直接后果：原 SQL 错误 |

### 9.2 修正后强制规范（v2.11.7 起）

#### 9.2.1 数据存储原则

**所有 SysEmployee / 类似业务表的字典外键字段遵循**：
- **字段名**：`xxxTypeId` / `xxxId` / `xxxStatusId` 等形式（FK 标准命名）
- **类型**：`INT`（外键主键）
- **默认值**：对应基础资料表的默认记录（如 `AttendanceTypeId = 1` 对应 DEFAULT）
- **字典表**：通过 `[Table("XxxType")]` 关联维护

#### 9.2.2 数据展示原则

**所有列表、表单、详情页的字典外键字段显示遵循**：
- **存储层**：FK ID（如 `attendanceTypeId: 3`）
- **页面层**：显示中文名（如"中班"）+ Badge 颜色（如 `bg-warning text-dark`）
- **页面渲染**：`XxxType.find(t => t.id === emp.xxxTypeId)?.name`

#### 9.2.3 关联引用单一数据源原则

**任何 FK 字段只能从一个数据源取**：
- 禁止在 2 个或更多表中冗余存储同一 FK 字段（如 `EMPLOYEE_BILLS.attendanceType` 同时存在 = FK 违规）
- 必须通过 FK 关联（JOIN 或 EF Core `Include`）从基础资料表取 Name
- 修改基础资料表 `Name` 后，所有引用页面**自动联动**（不需数据迁移）

### 9.3 mock-data.js 兼容性处理（v2.11.7.BUGFIX）

**问题**：mock-data.js PERSONNEL 数组存在数据格式不一致——619 条用旧格式 `attendanceType: "MIDDLE"`（字符串代码），仅 31 条用新格式 `attendanceTypeId`。

**解决方案**：在 `mock-data.js` 文件末尾追加 `normalizeData()` IIFE 自动规范化：

```javascript
(function normalizeData() {
    if (typeof PERSONNEL !== 'undefined') {
        PERSONNEL.forEach(p => {
            // 考勤班次补全（旧字符串 → FK + Name）
            if ((p.attendanceTypeId === undefined || p.attendanceTypeId === null) && p.attendanceType) {
                const t = ATTENDANCE_TYPES.find(x => x.code === p.attendanceType);
                if (t) { p.attendanceTypeId = t.id; p.attendanceTypeName = t.name; }
            }
            // 员工类型补全
            if ((p.employeeTypeId === undefined || p.employeeTypeId === null) && p.employeeType) {
                const t = EMPLOYEE_TYPES.find(x => x.code === p.employeeType || x.name === p.employeeType);
                if (t) { p.employeeTypeId = t.id; p.employeeTypeName = t.name; }
            }
            // ... 其他字段省略 ...
        });
    }
})();
```

**前端页面兼容性兜底**：所有访问 `emp.attendanceTypeId` 的代码增加 fallback 逻辑，同时兼容字符串代码（旧格式）：

```javascript
const attendanceLabel = (emp) => {
    if (!emp) return '-';
    if (emp.attendanceTypeId != null) {
        return ATTENDANCE_TYPES.find(x => x.id === emp.attendanceTypeId)?.name || '-';
    }
    if (emp.attendanceType) {
        return ATTENDANCE_TYPES.find(x => x.code === emp.attendanceType)?.name 
            || ATTENDANCE_NAME[emp.attendanceType] || emp.attendanceType;
    }
    return '-';
};
```
