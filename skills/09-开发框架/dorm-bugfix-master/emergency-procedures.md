# 紧急情况处理流程（Emergency Procedures）

> Skill: dorm-bugfix-master
> 创建日期：2026-07-28

---

## 概述

当遇到 🔴 P0 紧急 BUG 时（生产环境故障、隐私泄露、数据丢失），需要快速响应。
本流程定义**紧急情况下的标准化处理步骤**，避免慌乱中犯错。

---

## 紧急情况分类

| 等级 | 描述 | 响应时间 | 示例 |
|------|------|----------|------|
| 🔴 P0 严重 | 生产环境不可用 / 隐私泄露 | 立即（< 30 分钟） | 隐私字段全员可见、TrayApp 启动失败 |
| 🟡 P1 重要 | 重要功能 BUG | 24h 内 | 性别列缺失、密码重置不生效 |
| 🟢 P2 一般 | 一般问题 | 下个版本 | UI 不一致、文档缺失 |

---

## P0 紧急 BUG 流程

### 阶段 1：立即响应（5 分钟内）

**目标**：停止问题扩散

**步骤 1：停止发布**（如有未发布修改）
```bash
# 立即停止 TrayApp 拉起子进程
taskkill /F /IM DormManage.TrayApp.exe 2>&1
taskkill /F /IM DormManage.Admin.exe 2>&1
taskkill /F /IM DormManage.Api.exe 2>&1
```

**步骤 2：评估影响范围**
- 用户受影响范围：所有用户 / 部分用户 / 特定角色
- 数据影响：是否泄露 / 是否损坏
- 业务影响：核心功能是否可用

**步骤 3：通知相关人员**
- 用户：告知 BUG 正在修复
- 团队：通报 BUG 状态

### 阶段 2：快速诊断（30 分钟内）

**目标**：定位根因

**步骤 4：5 步排查**
1. 源码层确认（grep）
2. 编译层确认（dotnet build）
3. 发布时间戳确认（stat）
4. DLL 内容确认（注意 UTF-16 LE 编码）
5. 运行环境确认（ps -W）

**步骤 5：判断是否需要回滚**
- 是：进入"回滚流程"
- 否：进入"快速 patch"

### 阶段 3：快速 patch（2 小时内）

**目标**：最小变更修复

**步骤 6：编写最小修复**
- 只改需要改的代码
- 不要做大规模重构
- 避免引入新 BUG

**步骤 7：快速测试**
- 只测核心场景
- 跨权限测试必做
- 真实数据验证

**步骤 8：发布**
- 紧急发布包：`DormManage-v2.13.193-hotfix_紧急修复.zip`
- 用 sync 脚本发布

### 阶段 4：延后完善（24 小时内）

**目标**：完善文档和测试

**步骤 9：创建完整 BUG 修复文档**
- `00-方案文档/XXX-紧急BUG修复-v2.13.193.md`
- 包含：症状、根因、修复方案、教训

**步骤 10：更新 known-bugs.md**
- 添加新案例
- 更新查找表

**步骤 11：更新 CLAUDE.md**
- 在 Important Notes 段落添加版本备注

**步骤 12：补充测试用例**
- 添加到 `testing-checklist.md`
- 防止未来再次发生

## 回滚流程

### 何时回滚

- 🔴 紧急 patch 后仍然失败
- 🔴 引入新 BUG
- 🔴 数据损坏

### 回滚步骤

**步骤 1：停止所有进程**
```bash
taskkill /F /IM DormManage.TrayApp.exe
taskkill /F /IM DormManage.Admin.exe
taskkill /F /IM DormManage.Api.exe
sleep 3
```

**步骤 2：恢复备份**
```bash
# 找到最新备份
ls -la release.backup.*
# 恢复
mv release.backup.<最新时间戳> release
```

**步骤 3：启动旧版本**
```bash
cd release/latest/TrayApp
DormManage.TrayApp.exe
```

**步骤 4：验证旧版本工作**
```bash
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5001/
# 期望：200 或 302
```

**步骤 5：通知用户**
- "已回滚到 v2.13.X 版本"
- "BUG 修复中"
- "预计恢复时间"

## 紧急发布流程

### 跳过 sync 脚本的紧急发布（仅 P0 紧急时使用）

```bash
# 1. 紧急修改代码
# 2. 编译
dotnet build DormManage.sln -c Release

# 3. 手动复制到所有目录
cp release/latest/Admin/DormManage.Admin.dll release/latest/TrayApp/Admin/
cp release/latest/Admin/DormManage.Admin.dll release/latest/TrayApp/Api/  # 错误，但兼容
# 实际只复制到 TrayApp 子目录

# 4. 启动
taskkill /F /IM DormManage.TrayApp.exe
release/latest/TrayApp/DormManage.TrayApp.exe
```

**注意**：紧急发布后**必须**：
- 立即编写完整 BUG 修复文档
- 完整测试（不只是核心场景）
- 用 sync 脚本重新发布

## 紧急情况反模式（禁止）

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 慌乱直接改代码 | 引入新 BUG | 先停服务再分析 |
| 跳过测试直接发布 | 风险扩大 | 必须测试 |
| 不记录 BUG 修复 | 未来重复发生 | 必须文档化 |
| 私自决定回滚 | 沟通混乱 | 团队决策 |
| 隐瞒 BUG | 失去信任 | 主动报告 |

## 紧急情况案例库

### 案例 1：v2.13.193 隐私字段 deny-by-default 翻转
- **发现时间**：2026-07-27
- **紧急程度**：🔴 P0（隐私泄露）
- **影响范围**：所有未授权角色
- **处理流程**：5 步排查 → 找到根因 → 快速 patch → 同步发布
- **教训**：文档与代码必须同步 commit

### 案例 2：v2.13.193 发布双胞胎陷阱
- **发现时间**：2026-07-27
- **紧急程度**：🟡 P1（修改无效）
- **影响范围**：所有发布
- **处理流程**：5 步排查 → 找到根因 → 创建 sync 脚本
- **教训**：发布路径必须同步

### 案例 3：v2.13.193 账号有效期 `>` 应为 `>=`
- **发现时间**：2026-07-27
- **紧急程度**：🟡 P1（账户安全）
- **影响范围**：所有到期账号
- **处理流程**：5 步排查 → 找到根因 → 修复 + 统一助手函数
- **教训**：同一业务规则不要有多个独立实现

---

**使用建议**：紧急情况时**保持冷静**，按本流程执行，避免遗漏关键步骤！
