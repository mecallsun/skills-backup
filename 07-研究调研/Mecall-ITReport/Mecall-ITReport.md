# Mecall-ITReport

## 部门级IT信息化需求调研访谈与研究诊断报告

### 技能概述

本技能是面向**部门级IT信息化需求调研访谈与研究诊断报告**的标准封装：将IT负责人对业务部门/外部供应商的**深度访谈录音转写文本**（ASR输出），转化为一份极其严谨、专业的**议题归集结构化报告**（HTML格式）。

**核心定位**：充当"首席IT现状调研官"，将"调研方（IT经理）"与"受访方（业务部门负责人/外部供应商）"的角色对话，彻底溶解为结构化的"议题-角色观点-关键内容总结"陈述，并以**研究诊断报告**形式输出IT现状评估与数字化转型方案建议。

**ASR错字修正定位**：口语/ASR错别字隐式修正是**过程素材归集环节**，在分析诊断完成后即完成使命，**不纳入最终交付成果**。修正对照表仅作为内部参考，供生成报告时确保术语准确，最终报告中不再呈现此章节。

**适用范围**：
- ✅ 业务部门IT现状调研（财务/行政/HR/生产/研发/销售等）
- ✅ 数智化转型诊断（含IT顶层规划）
- ✅ 新厂IT顶层规划
- ✅ 外部供应商服务盘点（如电信运营商）
- ❌ 不适用于：销售/营销/学术/UX研究类访谈

### Step 1.5：角色识别与代入提问（无角色定义时必做）

```
目标：当资料素材中涉及多方对话但未标注角色时，
      需根据内容识别不同角色，为每个角色代入独立视角进行分析
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【触发条件】资料素材中出现以下情况时必须执行本步骤：
  ✓ 对话内容中出现"我/我们"但未定义说话人身份
  ✓ 多方观点混杂在同一段落中无法区分来源
  ✓ 同一话题有多个不同立场的表述但无角色标签
  ✓ 资料中包含"有人认为...另一些人认为..."但未明确主体

【角色识别四步法】
  1. 【识别发言者】通过称呼、语气、立场判断发言者身份
     - 称"我们公司"→ 可能是受访部门负责人或公司管理层
     - 称"你们IT"→ 一定是业务部门人员
     - 称"这个系统"→ 结合上下文判断是IT方还是业务方
     - 称"我之前在XX公司"→ 一定是受访方（业务部门）
     - 称"我们测试过"→ 可能是IT方或业务方，按内容判断

  2. 【角色归类与命名】
     - 调研方：IT负责人 / IT经理 / IT团队成员（代表IT部门立场）
     - 受访方（主）：业务部门负责人 / 部门主管 / 一线使用者（代表业务立场）
     - 受访方（辅）：其他参与对话的部门代表或外部人员
     - 第三方（如有）：外部供应商 / 外部专家（代表外部视角）
     - 若同一部门有多人发言，可标注为"受访方-A" / "受访方-B"

  3. 【代入角色提问与回复分析】
     为每个识别出的角色分别代入其立场，分析其主题关注点和对话思维：
     ┌─────────────────────────────────────────────────────────┐
     │ 角色A（调研方 - IT负责人）                               │
     │  → 关注点：技术可行性、架构规范、数据安全、成本控制        │
     │  → 思维模式：问题诊断 → 技术方案 → 实施路径 → 资源需求   │
     │  → 典型表达："这个方案技术上可行"、"我们需要考虑..."     │
     ├─────────────────────────────────────────────────────────┤
     │ 角色B（受访方 - 业务部门负责人）                          │
     │  → 关注点：业务效率、用户体验、工作负担、系统易用性        │
     │  → 思维模式：痛点描述 → 期望解决 → 资源/权限诉求        │
     │  → 典型表达："用起来很麻烦"、"希望能自动..."、"每次都要..." │
     ├─────────────────────────────────────────────────────────┤
     │ 角色C（如有 - 外部供应商）                                │
     │  → 关注点：服务能力、产品优势、合作条件、商务条款         │
     │  → 思维模式：能力展示 → 方案推荐 → 商务承诺             │
     │  → 典型表达："我们可以提供..."、"这个功能已经实现了"     │
     └─────────────────────────────────────────────────────────┘

  4. 【输出角色-话题映射表】
     基于识别结果，输出角色-话题映射（内部参考，不纳入交付报告）：
     ┌──────────┬──────────────┬──────────────────┬─────────────────┐
     │ 角色     │ 核心立场    │ 关注话题         │ 关键诉求        │
     ├──────────┼──────────────┼──────────────────┼─────────────────┤
     │ IT负责人  │ 技术管控    │ 网络/监控/安全   │ 规范、可控      │
     │ 行政负责人│ 效率提升    │ 报餐/考勤/门禁   │ 减负、便捷      │
     │ 供应商   │ 商务合作    │ 产品/服务/SLA    │ 签约、维护      │
     └──────────┴──────────────┴──────────────────┴─────────────────┘

【关键原则】
  - 宁可多识别几个角色，不可遗漏任何有独立立场的声音
  - 同一角色在不同话题中可能有关注差异，需按议题分别代入
  - 角色代入是为了深度分析，不是为了对立，而是为了全面理解
  - 最终报告中不出现角色标注，只输出议题归集结论
```

### Step 2：语意话题拆解与议题归集

```
目标：彻底摒弃对话时间线，按上下文语意拆分为独立议题
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

议题归集方法：
  1. 通读全文，识别语意转折点（如"还有..."、"另外..."、"最后..."）
  2. 按"问题-方案-确认"三段式切分
  3. 将同一主题的多个对话片段归并为一个议题
  4. 议题优先级建议：基础设施/数据治理 > 业务系统 > 战略规划

议题命名规范：
  格式："议题X：[核心痛点主题]"
  示例：议题1：考勤系统与HR系统两供应商数据未打通（核心痛点）
  
议题数量原则：
  - 不限数量，必须根据访谈内容全面且完整地归集主题
  - 按实际内容归集，有多少独立话题就归集多少议题
  - 每个议题聚焦一个独立的IT/信息化话题
  - 宁可细分不可合并遗漏，确保访谈中提及的所有IT/信息化话题均有对应议题
```

### Step 3：按角色结构化总结关键内容（禁止输出对白）

```
目标：每个议题按"受访方-调研方"双方视角总结
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【四要素输出结构】

议题X：[议题标题]
  ├─ 受访方（业务部门负责人/外部供应商）关键内容总结
  │   ├─ 真实业务现状（基于原文事实）
  │   ├─ 历史遗留技术债
  │   ├─ 业务痛点（具体数据/案例）
  │   └─ 对IT的具体诉求
  │
  ├─ 调研方（IT经理）关键内容总结
  │   ├─ 引导性建议
  │   ├─ 对公司IT规范的重申
  │   ├─ 初步技术路径解释
  │   └─ 给予的资源承诺
  │
  ├─ 基于真实的【IT现状评估】
  │   ├─ 当前系统/服务现状
  │   ├─ 存在的实际风险与瓶颈
  │   └─ 数据/案例支撑
  │
  └─ 基于真实的【数字化方案建议】
      ├─ 速赢项（1-3个月可落地）
      ├─ 中期项目（3-6个月）
      └─ 长期演进（6-12个月以上）

要求：
  - 用高度结构化的公文语言
  - 一字不少地保留核心业务实质
  - 严禁保留任何"发言人对白/台词"的过程内容
```

### Step 4：基于真实的评估与方案建议

```
目标：100%基于原文真实内容输出IT评估与方案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

IT现状评估原则：
  - 风险等级：P0（极高/立即处理）→ P1（高/3个月内）→ P2（中/6个月）→ P3（低/长期）
  - 评估维度：成熟度（高/中/低/空白）× 紧急度（极高/高/中/低）
  - 数据支撑：必须引用原文中的具体数据
  - 避免套话：每条评估必须可追溯到原文某段具体表述

数字化方案建议原则：
  - 技术可行性：基于IT负责人自述的能力边界
  - 成本可承受：投入产出比合理
  - 实施路径：分阶段、可执行、有责任方
  - 风险预案：考虑落地阻力
```

## 五、🎯 商务情商原则（基于6份V4报告实战经验）

商务情商是本技能的关键进化要点，确保报告<strong>事实准确、表达得体、合规可控</strong>。

### 5.1 职级表述严谨化

```
原则：报告中的职级必须与公司实际岗位设置一致
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 正确表述：
  - IT经理（IT负责人·刘巍）   ← 金戈新材IT负责人实际职级
  - 财务部陈经理               ← 财务经理
  - 行政部谢主管               ← 行政主管

❌ 错误表述（自动提升职级）：
  - IT总监 / 信息总监          ← 实际为经理级
  - 信息总监（IT负责人）      ← 同上
  - 信息总监一人多角           ← 错误，应为"IT经理一人多角"

处理方法：
  1. 凡涉及金戈公司IT负责人，统一用"IT经理（IT负责人·刘巍）"
  2. 严禁使用"信息总监""IT总监"等不存在的职级
  3. 能力描述可保留（"四角色经验""AI/IoT背景"等），但职级必须匹配
```

### 5.2 受访方角色定位严谨化

```
原则：明确区分"内部业务部门" vs "外部供应商"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 内部业务部门（六大部门）：
  - 财务部、行政部、HR部、生产部、研发部、销售部
  - 定位："受访部门"
  - 角色："业务方"（公司内部）

❌ 外部供应商（必须明确定位）：
  - 电信运营商、IT外包商、设备供应商等
  - 定位："受访对象（外部供应商）"
  - 角色："乙方/外部服务商"
  - 必须明确"非金戈内部所属部门"
  - 必须明确"甲乙双方关系"

错误案例：❌ "电信部IT现状调研报告"
正确案例：✅ "中国电信运营商服务IT信息化需求调研访谈与研究诊断报告"
```

### 5.3 评估方案表述降级化

```
原则：去除营销性"评估方案"表述，改为客观"参考"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 商务情商正确表述：
  - "可参考XX方案"          ← 客观参考
  - "通过正式评估流程决定"  ← 合规表述
  - "为可选升级方向"         ← 中性表述
  - "待定/参考"             ← 表格标签

❌ 营销性表述（已剔除）：
  - "评估XX方案"            ← 营销断言
  - "评估是否..."            ← 主观预判
  - "对比评估XX方案"         ← 推销
  - "评估升级"               ← 推销

处理方法：
  1. "评估XX方案" → "XX方案可能性参考" 或 "可参考XX方案"
  2. "评估是否..." → "可参考继续...或重新..." 
  3. "对比评估" → "对比参考"
  4. "评估升级" → "升级参考" 或 "为可选升级方向"
  5. 表格中"待评估" → "待定"
```

### 5.4 营销性前瞻表述剔除

```
原则：去除AI/大数据/数字孪生等营销性前瞻表述
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 客观事实保留：
  - 电信业务经理提及"公司整体能力在持续提升"
  - 电信在能力提升方向上的投入
  - 仅为访谈氛围层面的提及

❌ 营销性表述（已剔除）：
  - "AI/大数据合作——探索AI算力/数据中台合作"
  - "数字孪生+大数据合作"
  - "AI/大数据能力"作为合作卖点

处理方法：
  1. "AI/大数据合作" → "能力建设关注（具体方向未展开）"
  2. "数字孪生+大数据合作" → 完全删除
  3. "AI算力/数据中台" → 完全删除
  4. "电信的AI/大数据能力" → "能力持续提升（具体方向未展开）"
```

### 5.5 合作伙伴中性化

```
原则：避免"首选/第一选项"等主观断言，改为中性描述
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 商务情商中性表述：
  - "长期合作伙伴之一"        ← 客观事实
  - "新厂建设期需通过竞争性谈判" ← 流程合规
  - "需通过正式评估确定"       ← 治理规范
  - "为可选合作方案"            ← 中性表述

❌ 主观断言表述（已纠正）：
  - "首选合作伙伴"             ← 主观断言
  - "第一选项"                 ← 主观断言
  - "全面合作"                 ← 过度承诺
  - "深度合作"                 ← 营销词

处理方法：
  1. "首选合作伙伴" → "长期合作伙伴之一（需通过竞争性谈判确定）"
  2. "第一选项" → "长期合作伙伴之一"
  3. "全面合作" → "可参与竞争性谈判"
  4. "深度合作" → "可参与"
```

### 5.6 数据严谨化（避免绝对断言）

```
原则：保留可量化数据，弱化定性断言
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  - "某型号单价150元/只"
  - "150间宿舍月总费用约7000元"
  - "访谈中提及/在XX条件下"

❌ 模糊化绝对断言：
  - "最优选"                  ← 主观断言
  - "全面最佳"                ← 绝对断言
  - "业界领先"                ← 营销词
```

## 十二、⚠️ 常见陷阱与规避（基于6份报告实战教训）

### 陷阱1：脱离原文凭空想象

```
❌ 错误："建议引入AI客服系统"（原文未提及）
✅ 正确："建议基于现有云之家扩展工作流应用"（基于原文实际系统）
```

### 陷阱2：保留对话过程

```
❌ 错误："陆主管说：'我们IT的话可能一个成熟面'..."
✅ 正确："HR部对当前IT整体服务给予'还行'评价，但对投入产出比强烈不满..."
```

### 陷阱3：方案过于空泛

```
❌ 错误："建议加强信息化"（无可执行性）
✅ 正确："短期（1-3个月）：启用云之家工资条功能，员工手机自助查询"
```

### 陷阱4：忽视数据支撑

```
❌ 错误："考勤数据滞后严重"（无数据）
✅ 正确："报餐322人实际到400+人，差距30%+"（具体数据）
```

### 陷阱5：未区分角色

```
❌ 错误：议题总结未区分"调研方"与"受访方"观点
✅ 正确：每议题严格按"受访方/调研方"双方视角分别总结
```

### 陷阱6：职级表述错误（商务情商）

```
❌ 错误：信息总监 / IT总监（实际为经理级）
✅ 正确：IT经理（IT负责人·刘巍）
```

### 陷阱7：内部/外部角色混淆（商务情商）

```
❌ 错误：将中国电信称为"电信部"（作为内部部门）
✅ 正确：中国电信作为外部运营商供应商（非内部所属部门）
```

### 陷阱8：营销性评估方案表述（商务情商）

```
❌ 错误："评估XX方案"、"评估升级"、"对比评估"
✅ 正确："可参考XX方案"、"升级参考"、"对比参考"
```

### 陷阱9：AI/大数据前瞻营销表述（商务情商）

```
❌ 错误："AI/大数据合作——探索AI算力/数据中台合作"
✅ 正确："能力建设关注（具体方向未展开）"
```

### 陷阱10：合作伙伴主观断言（商务情商）

```
❌ 错误："首选合作伙伴"、"第一选项"
✅ 正确："长期合作伙伴之一（需通过竞争性谈判确定）"
```

### 陷阱11：未明确甲乙方关系（外部供应商）

```
❌ 错误：调研方/受访方（外部供应商场景下未明确）
✅ 正确：调研方（甲方）/ 受访方（乙方）
```

### 陷阱12：调研核心目的描述含"评估方案"动作

```
❌ 错误：核心目的包含"评估XX方案"动作
✅ 正确：核心目的描述"识别优化空间/厘清诉求/建立机制"
```

### 陷阱13：覆盖已有版本文件（版本号未递增）

```
❌ 错误：直接覆盖已有报告文件，如将 V4.0 覆盖为新的 V4.0
✅ 正确：每次生成必须在上次版本号基础上 +1
         如已有 行政调研_咨询报告_V4.0.html
         新生成文件必须命名为 行政调研_咨询报告_V4.1.html
```

### 陷阱14：资料含多方对话但未识别角色直接归并

```
❌ 错误：将不同角色的发言混在一起分析，未区分来源
✅ 正确：先识别发言者身份（IT方/业务方/外部供应商等）
         为每个角色代入其立场分别分析
         最终输出角色-话题映射后再归并到议题
```

## 十五、🔒 隐私敏感词规避规范（成果文件输出强制规范）

### 15.1 核心红线

```
┌─────────────────────────────────────────────────────────┐
│ 🔒 隐私红线：成果文件（含HTML报告/PPT/Word等交付物）必须遵守 │
├─────────────────────────────────────────────────────────┤
│ 1. 【禁止"录音"字眼】                                      │
│    所有对外交付的成果文件中严禁出现"录音"二字及其衍生词汇。    │
│    原始访谈素材属于内部隐私资产，不得在客户/管理层可见的        │
│    报告中暴露"录音"原始形态。                                │
├─────────────────────────────────────────────────────────┤
│ 2. 【禁止原始素材形态描述】                                  │
│    不得在报告中出现：录音文件、录音时长、录音设备、             │
│    录音转写、ASR错字等涉及原始采集过程的字眼。               │
│    报告应呈现的是"诊断结论"，而非"调研过程"。               │
├─────────────────────────────────────────────────────────┤
│ 3. 【过程素材与交付物严格隔离】                              │
│    内部过程素材（错字修正、原文片段、角色对白）               │
│    仅供分析阶段使用，不得以任何形式出现在最终成果文件中。      │
└─────────────────────────────────────────────────────────┘
```
